# pm-prd-generator 使用说明

> 一个把「资深产品经理 → 可评审 PRD」的过程固化成六阶段的 Skill。
> 版本 1.1.0 · 2026-10-25 · **自包含**（内置规范见 `references/00_PRD编写规范.md`，不依赖外部文件）

## 一、它是干什么的

给 Agent 一段口头需求（哪怕只有两句话），它会按六阶段往下走：

```
需求澄清 → 十个关键问题 → 需求分析报告 → PRD 八项要求 → 原型与 HTML → 自查交付
```

三个阶段性的硬约束，是它和「直接让 AI 写 PRD」最大的区别：

1. **第一步不写 PRD**。先复述理解、给粗方案，人点头了才往下走（原文明确要求「先不要直接写 PRD」）。
2. **需求由人来定**。中间强制提 10 个关键问题，每个问题都必须能回答「答错会写坏哪条需求」，Agent 不许自己编答案。
3. **每条都能被机器核**。PRD 写完后跑 `scripts/prd_lint.py`，8 条硬要求缺一项就报出来。

## 二、什么时候用

用得上的场景：

- 「帮我写个 PRD」/「给我做个需求分析」/「这个需求先帮我理清楚」/「画个原型图」。
- 有个模糊的产品想法，需要先被问清楚，再落成文档。
- 存量工具要改版，需要先盘现状再写需求。

用不上的场景：

- 只要技术方案 / 只要 UI 视觉稿 / 只要代码 —— 那是 `quality-dev-management` 或施工流程的事。
- 只想让你润色一份已经定稿的 PRD 措辞。

## 四、安装与怎么用

### 4.1 安装

本包是标准 Skill 目录结构（`SKILL.md` + `references/` + `scripts/`），**零依赖**（脚本只用 Python 标准库，Python 3.8+）。

把整个 `pm-prd-generator/` 目录放到你的 skills 目录下：

| 环境 | 放置位置 |
|---|---|
| WorkBuddy | `~/.workbuddy/skills/pm-prd-generator/`（Windows：`C:\Users\<你>\.workbuddy\skills\`） |
| Claude Code 及兼容实现 | 对应的 skills 目录，如 `~/.claude/skills/pm-prd-generator/` |
| 没有 skills 机制 | 放哪都行 —— 把 `SKILL.md` 直接喂给模型，或按 4.2 手动执行 |

`SKILL.md` 的 frontmatter 会被自动识别；**目录名要与 `name` 字段一致**，否则部分实现不识别。

### 4.2 三种用法

**作为 Skill 使用**：装好后在对话里说出触发词即可，Agent 会按 `SKILL.md` 的六阶段索引推进，并按需读取 `references/` 下的对应文档。

**手动照做使用**：把 `SKILL.md` 当流程卡，每进一个阶段打开对应 reference，照「操作步骤」编号做，用「输出模板」填空，交付前对照「反例」自检一遍。

**只想要机器判据**：

```bash
python scripts/prd_lint.py 你的PRD.md
# rc=0 全过 / rc=1 有缺项（打印清单，带行号）/ rc=3 判据不可用（文件不存在/读不了/空文件）
```

8 项检查：五步留痕表 · R 三行字段 · F 五要素 · 异常五类 · AC 三段句式 · 状态流转表 · 业务流程图 · 本期不做什么。

脚本自带自检：

```bash
python scripts/prd_lint.py --selftest
# 内置 1 份合格样例（断言 rc=0）+ 1 份故意缺项样例（断言 rc=1）
# 自检通过返回 0；自检本身失败返回 2
```

## 五、六阶段速查

| 阶段 | 一句话 | 产出 | 结束条件 |
|---|---|---|---|
| S1 | 我理解成了什么 + 大致怎么做 | 四栏理解表 + 2~3 条路线 | 用户说「对」 |
| S2 | 我还没搞清的 10 件事 | 问题表（挂「答错会写坏哪条」） | 用户答了 ≥7 条 |
| S3 | 事实和底数摆上桌 | 需求分析报告 | 用户确认报告 |
| S4 | 按规范落条款 | PRD_v1.0.md | lint rc=0 |
| S5 | 给人看的图 | 原型.html / PRD.html | 断网能开、图挂得上 F |
| S6 | 十条逐条过 | 自检表 + 交付说明 | 10 条全有证据 |

## 六、让它跑得更好的三个习惯

1. **问题阶段别催**。S2 的 10 个问题答得越具体，S4 返工越少；含糊回答（「你定」）会被记成未决项，最后还是要你定。
2. **给路径，别给描述**。有既有文档、既有代码就把路径贴进来，S3 才查得到实测数字，PRD 的现状章才有出处。
3. **看图提意见，别改字**。S5 的原型是给人挑毛病的；发现图上多出按钮，说明 PRD 少写了一条，回 S4 补，⛔ 不要在图上"先画着"。

## 七、已知局限

- 不替代真实用户访谈：10 个问题必须人来答，Agent 只负责问对。
- 不做竞品实测：对标停在公开方法论层面，替不了真跑一遍竞品。
- 只查形态不查内容：`prd_lint.py` 判"有没有、全不全"，判不了"价值成不成立、AC 是否真可测"。
- 原型是静态 SVG 示意，不是可用 UI。
- 不覆盖施工、自测、红蓝攻防、独立审查 —— 那一段属 `quality-dev-management`，且它只读本 PRD、⛔ 不许私改需求。

## 八、维护

- 改 PRD 章节骨架 → 改 `references/00_PRD编写规范.md` §二，本包其余文件只引用、⛔ 不再写第二份。
- 改 8 条硬要求 → 同时改 `scripts/prd_lint.py` 的 `CHECKS` 与 `--selftest` 样例，⛔ 不许只改文档。
- 每次改动后跑 `python scripts/prd_lint.py --selftest` 与 `python -m py_compile scripts/prd_lint.py`。
