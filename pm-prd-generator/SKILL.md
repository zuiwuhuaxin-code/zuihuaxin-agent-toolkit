# pm-prd-generator

把「资深产品经理从一段口头需求走到可评审 PRD」的过程固化为六阶段流水线。每个阶段有独立说明文档、独立判据、独立禁止项；跨阶段只有一条硬规矩——**上一阶段的产出是下一阶段的唯一输入**。

## 一、这个 Skill 解决什么

口头需求直接落到 PRD，会同时坏三件事：理解偏差没人纠、关键问题没人答、条款无法被第三方核。本 Skill 把这三件事拆成阶段，逼出偏差、逼出问题、逼出可核条款。

适用：从 0 到 1 的产品需求、存量工具的需求改写、容器型项目的编排需求。
不适用：纯技术方案设计、UI 视觉稿、代码实现（那是 `quality-dev-management` 的活）。

三种最常见的失败模式，本 Skill 的六阶段就是对着它们设计的：

| 失败模式 | 表现 | 对应阶段 |
|---|---|---|
| 理解偏差被焊进文档 | 第一条回复就写「1. 产品概述 2. 功能需求」 | S1 强制只出理解陈述 |
| 需求由 Agent 自己编 | 用户没说的事被写成「用户需要」 | S2 只提问不代答 |
| 条款不可核 | 「提升效率」「体验流畅」写满全篇 | S4 八条硬要求 + S6 lint |

## 二、硬前提（开工前必读，违反即返工）

**R1 铁律 —— S1 阶段禁止直接写 PRD。** 用户给需求后的第一份产出必须是「我理解成了什么 + 大致怎么做」的陈述，不是 PRD 章节。原文明确要求「先不要直接写 PRD」；跳过 S1 直接出文档，等于把理解偏差焊进 PRD。

**R2 判据只有一处定义。** 两类内容都收在包内 `references/00_PRD编写规范.md`，⛔ 不在别处另造一套：

- 五步走（调查事实 → 摸清底数 → 对标成熟方案 → 先出方案 → 最后执行）：见 `references/00_PRD编写规范.md` §1.2，含每步的硬要求与判据列。⛔ 不改词、不重排、不省略判据。
- PRD 章节骨架、表格字段、SVG 画法、HTML 规范、质量自检 10 条：唯一源是 `references/00_PRD编写规范.md` §二~§七。本 Skill 只讲「怎么驱动 Agent 按它写」，⛔ 不复制骨架当第二套标准。

> **本 Skill 自包含**：装进任何环境都能直接跑，不依赖外部规范文件。若你的团队已有自己的 PRD 规范，把 `references/00` §二 的骨架换成你们的即可 —— 但**只许有一份**，别让两套骨架并存。

**R3 事实与推断分离。** 事实写实测数字并附路径或命令；推断标【推断】；查不到写「未核实」。⛔ 不编造数字、日期、人名。

**R4 每阶段先写「不做什么」。** 动手前写明本次拒绝做什么，并给理由。多数事故不是做错了，而是做了不该做的。

**最短路径（记住这一句就够开工）**：先复述理解、再提 10 个问题让人答、再出分析报告、再照规范写 PRD、再画原型出 HTML、最后 lint + 10 条自检。第一步 ⛔ 不许写 PRD。

**开工前置检查（五条全过才动手）**：

1. 明确当前处于 S1~S6 哪一阶段，上一阶段的产出是否已到手。
2. 打开 `references/00_PRD编写规范.md`，确认可读（S4 起必需，S1/S2 可先不看骨架）。
3. 确认用户是否为「能回答问题的人」；若不能，S2 的问题清单要写明需要谁答。
4. 确认交付目标是「评审用」还是「施工用」——前者重在取舍，后者重在可测。
5. 写下本次「⛔ 不做什么」至少 3 条。

## 三、六阶段总览

| 阶段 | 名称 | 核心动作 | 产出 | 说明文档 |
|---|---|---|---|---|
| S1 | 需求澄清 | 复述理解 + 给 2~3 条思路方案，⛔ 不写 PRD | 理解陈述 + 思路方案 | `references/01_需求澄清.md` |
| S2 | 十个关键问题 | 提 10 个真问题，禁臆断禁硬凑，每个挂「答错会写坏哪条需求」 | 问题清单（待人来答） | `references/02_十个关键问题.md` |
| S3 | 需求分析报告 | 五步走前两步（调查事实 + 摸清底数）→ 出报告 | 需求分析报告 | `references/03_需求分析报告.md` |
| S4 | PRD 生成 | 按内置规范落 8 条硬要求 | `PRD_v1.0.md` | `references/04_PRD八项要求.md` |
| S5 | 原型与 HTML | SVG 原型图 + 单文件 HTML 交付 | `原型.html` / `PRD.html` | `references/05_原型与HTML交付.md` |
| S6 | 自查与交付 | 质量自检 10 条逐条过 + 写交付说明 | 自检表 + 交付说明 | `references/06_自查与交付.md` |

阶段串行，⛔ 不许跳步、不许合并。可回退：S4 发现需求有歧义 → 退回 S2 补问题；S5 发现 PRD 缺状态 → 退回 S4 补章。回退要在回复里写明「退回哪一阶段、补什么」，⛔ 不静默改需求。

**三道闸，过不了不许进下一阶段**：

| 闸 | 位置 | 判据 | 不过怎么办 |
|---|---|---|---|
| 闸一 | S1 → S2 | 用户已确认理解无偏差 | 重写复述，⛔ 不进 S2 |
| 闸二 | S3 → S4 | 用户已确认分析报告，未决项单列 | 补问题、补数据 |
| 闸三 | S6 → 交付 | lint rc=0 且 10 条自检全有证据 | 修到过为止，⛔ 不带缺项交付 |

**各阶段读者**（写的时候想着谁在读）：

| 阶段 | 主要读者 | 读它来干什么 |
|---|---|---|
| S1 | 提需求的人 | 纠偏差 |
| S2 | 提需求的人 | 答题 |
| S3 | 提需求的人 / 需求评审 | 判断需求成不成立 |
| S4 | 需求评审 / 施工角色 | 核需求、照功能点干活 |
| S5 | 决策者 / 非技术评审 | 一眼看懂界面长什么样 |
| S6 | 需求评审 | 判断能不能收

## 四、S1 需求澄清

- **输入**：用户的需求原话（可含链接、截图、既有文档路径）。
- **动作**：
  1. 逐句拆用户原话，填四栏：要做什么 / 给谁用 / 什么场景下用 / 成功长什么样。
  2. 给 2~3 条粗方案路线，每条标「代价 + 风险 + 我倾向哪条及理由」，只给方向，不做到字段级。
  3. 列出「我还没听懂的地方」≤3 条，作为 S2 问题清单的种子。
  4. 收尾固定一句：「以上理解如无偏差，我进入 S2 提 10 个问题」。
- **产出**：一屏内的理解陈述 + 思路方案。
- **⛔ 本阶段不做什么**：不写 PRD 任何章节；不给字段设计、不排期、不估工作量；不下「需求成立/不成立」的终判。
- **完成判据**：四栏都有内容；用户回「对/不对」并能指出偏差；回复中不出现 PRD 章节标题。
- **常见走样**：把「大致思路」写成分层架构图（那是技术方案，不是产品思路）；复述只换词不复述场景，用户看不出你到底听懂了没有。
- **读**：`references/01_需求澄清.md`。

## 五、S2 十个关键问题

- **输入**：S1 的理解陈述 + 用户对偏差的纠正。
- **动作**：
  1. 从角色、边界、数据、异常四个来源拉候选问题池，≥15 条。
  2. 删掉「我自己能查到」和「答了也不影响任何需求」的，剩下的才配进 10 条。
  3. 每条挂两样：为什么要问（指向某条 R/F/AC）、**答错会写坏哪条需求的具体后果**。
  4. 按「不问就没法写 PRD」排序，前 5 条必须是阻塞级。
  5. 交人回答，⛔ 不替用户编答案。
- **产出**：Q-01~Q-10 问题表（含待确认的默认假设）。
- **⛔ 本阶段不做什么**：不硬凑数量（宁可 8 条也不编 2 条）；不把假设写成结论；不趁提问夹带方案定稿。
- **完成判据**：10 条（或说明为何不足 10 条）每条都有「答错会写坏哪条」；用户已逐条回填 ≥7 条。
- **常见走样**：问题里夹带答案（「是不是应该加个队列？」）；10 条问题全指向同一件事，等于只问了 1 个。
- **读**：`references/02_十个关键问题.md`。

## 六、S3 需求分析报告

- **输入**：S2 已回填的问题表。
- **动作**：
  1. 按 `references/00_PRD编写规范.md` §1.2 五步走的前两步执行：**调查事实**（查现状，给实测数字与路径）、**摸清底数**（盘既有机制与存量：已有什么 / 缺什么 / 多少）。
  2. 把 S2 的回答逐条回填进报告，未答的进「未决」。
  3. 出需求候选清单与优先级初判，每条挂到 §2 的某条卡点上。
  4. 报告末尾单列「未决与风险」，交人确认后才进 S4。
- **产出**：需求分析报告（结构见 reference）。
- **⛔ 本阶段不做什么**：不走完五步的后三步（对标、方案、执行）就写 PRD；不出现无出处的数字；不把【推断】升级成事实。
- **完成判据**：每个数字有出处（路径或命令）；「已有什么/缺什么/存量多少」量化；用户已确认报告。
- **常见走样**：报告只有结论没有底数；写「存量代码约几千行」这种没有出处的估算。
- **读**：`references/03_需求分析报告.md`。

## 七、S4 PRD 生成

- **输入**：已确认的需求分析报告 + `references/00_PRD编写规范.md`。
- **动作**：
  1. 照 `references/00_PRD编写规范.md` §二 的 14 章骨架建文档，章节号与顺序不动。
  2. 八条硬要求逐条落到可核形态：R 三行字段 / F 五要素 / AC「给定·当·那么」/ 状态表 / 流程图（含异常分支）/ 本期不做什么 / 五步走留痕 / 异常五类必备。
  3. 每条 R 的「解决什么问题」挂回 S3 报告的具体卡点；每条 AC 指向具体 F 编号。
  4. 写盘用 Python `write_text(text, encoding="utf-8", newline="\n")` 或 `write_bytes`，纯 LF。
- **产出**：`PRD_v1.0.md`。
- **⛔ 本阶段不做什么**：不新增规范外的章节结构；不写不可判词（「体验良好」「尽量快」）；不把未决项藏进正文（必须进风险章）。
- **完成判据**：`python scripts/prd_lint.py PRD_v1.0.md` 返回 rc=0。
- **常见走样**：AC 写成「功能正常可用」；状态表与流程图的状态名不一致（一个写「待导入」一个写「待处理」）。
- **读**：`references/04_PRD八项要求.md`。

## 八、S5 原型与 HTML 交付

- **输入**：已过 lint 的 `PRD_v1.0.md`。
- **动作**：
  1. 按 `references/00_PRD编写规范.md` §五 画 SVG 原型图，每张图下配「原型说明」并标出对应的 F 编号。
  2. 按同文件 §六 出单文件 HTML：内联 style、SVG 内嵌、⛔ 不引外部 CSS/JS/CDN。
  3. 每张原型必须能指回至少一个 F；指不回的图删掉。
- **产出**：`原型.html`、`PRD.html`。
- **⛔ 本阶段不做什么**：不引 CDN 与外链字体；不在 HTML 里偷改 PRD 内容（HTML 与 MD 必须同源）；不做交互逻辑实现。
- **完成判据**：断网可打开；SVG 无外部引用；原型与 F 编号一一对得上。
- **常见走样**：HTML 里出现 `https://cdn...`；原型图上冒出 PRD 没写的按钮，等于在图上偷偷加需求。
- **读**：`references/05_原型与HTML交付.md`。

## 九、S6 自查与交付

- **输入**：PRD.md + HTML + lint 结果。
- **动作**：
  1. 跑 `python scripts/prd_lint.py PRD_v1.0.md`，rc≠0 先修再谈交付。
  2. 按 `references/00_PRD编写规范.md` §七 的 10 条逐条人读，逐条填「过/不过 + 证据」。
  3. 写交付说明：交付物清单、判据结果、已知缺陷、未决项、下一步交给谁。
  4. 交需求评审；下一段（`quality-dev-management`）只读 PRD，⛔ 不许在施工中私改需求。
- **产出**：自检表 + 交付说明。
- **⛔ 本阶段不做什么**：不把缺项写成「后续补」当交付；不用「已自测」替代逐条证据；不自审自判独立审查。
- **完成判据**：10 条全有结论与证据；lint rc=0；交付说明含未决项与接收方。
- **常见走样**：自检表十行全写「通过」却无证据；未决项被顺手删掉当成已解决。
- **读**：`references/06_自查与交付.md`。

## 十、脚本：prd_lint.py

零依赖、纯标准库，检查一份 PRD md 是否满足 8 条硬要求。

```bash
python scripts/prd_lint.py <prd.md>      # 0 全过 / 1 有缺项 / 3 判据不可用
python scripts/prd_lint.py --selftest    # 内置 1 合格 + 1 缺项样例，断言 rc=0 / rc=1
```

8 条检查项：五步留痕表、R 三行字段、F 五要素、异常五类、AC 三段句式、状态流转表、业务流程图、本期不做什么。
输出逐条 `[PASS]/[FAIL]`，缺项带行号；rc=3 用于文件不存在、读不了、内容为空。自检失败返回 rc=2。

## 十一、交付物清单

```
<项目名>_PRD_v1.0.md      # 主交付，过 lint
<项目名>_PRD_v1.0.html    # 单文件、离线可开
<项目名>_原型.html        # SVG 原型，挂 F 编号
需求分析报告.md           # S3 产出，PRD 的原料
自检表 + 交付说明         # S6 产出
```

## 十二、已知局限

- 本 Skill 不替代真实用户访谈。S2 的 10 个问题必须由人来答，Agent 只能提问、⛔ 不能代答。
- 本 Skill 不做竞品实测。S3 的「对标成熟方案」只能给公开方法论层面的映射，替不了真跑一遍竞品。
- 本 Skill 不校验业务正确性。「为谁做/解决什么问题/带来什么价值」写得齐不等于写得对，业务判断仍需人拍板。
- `prd_lint.py` 只查形态（有没有、全不全），⛔ 不查内容质量（价值是否成立、AC 是否真可测）。
- 原型图为静态 SVG 示意，不等于可用 UI；视觉细节以 UI 规范单独文档为准。
- 本 Skill 不覆盖施工、测试、红蓝攻防、独立审查，那一段属 `quality-dev-management`。

- 每次改动后必跑三条：`python scripts/prd_lint.py --selftest`、`python tests/test_prd_lint.py`、`python -m py_compile scripts/prd_lint.py`。
- **改判据后必做元验证**：把判据换成已知有错的实现，`tests/` 必须变红。一直绿的测试只证明「代码没崩」，不证明「判据能抓」。
