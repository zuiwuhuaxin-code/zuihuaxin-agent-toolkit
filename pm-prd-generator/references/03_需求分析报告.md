# S3 需求分析报告 —— 五步走前两步的落点

> 阶段定位：在写 PRD 之前，先把「事实」和「底数」摆上桌。这一步不是写文档，是**先把地踩实**。
> 上游：`02_十个关键问题.md`。下游：`04_PRD八项要求.md`。

## 一、目标与判据

**目标**：产出一份「每个数字都有出处、每句判断都挂着事实」的分析报告，让 PRD 的每一条需求都能指回某个真实卡点，而不是指回某个想法。

**本阶段只走五步走的前两步**（后三步留给 S4/S5/S6）：

> 五步走原文（`00_PRD编写规范.md` §1.2）：
> 「调查事实、摸清底数、对标成熟方案、先出方案、最后执行。想清楚不做什么，比想做什么更重要。」
> ⛔ 不转述、不重排这五步，本文件只规定**每一步落在本阶段的哪个章节**。

| 步 | 本阶段做什么 | 落在报告哪一节 |
|---|---|---|
| 1 调查事实 | 查现状，给实测数字与路径 | §1 调查事实 |
| 2 摸清底数 | 盘既有机制与存量：已有什么/缺什么/多少 | §2 摸清底数 |
| 3 对标成熟方案 | 本阶段只记「待对标清单」，结论留到 PRD §3 | §5 待办移交 |
| 4 先出方案 | 本阶段只出需求候选与优先级初判，⛔ 不写条款 | §4 需求候选 |
| 5 最后执行 | 本阶段不做 | — |

**判据（全过才算完成）**：

| # | 判据 | 判定方式 |
|---|---|---|
| 1 | §1 每条事实都有路径或命令 | 抽 3 条回查文件是否真实存在 |
| 2 | §2 三项量化齐全：已有什么 / 缺什么 / 存量多少 | 逐项检查，缺一即未过 |
| 3 | 每条需求候选都挂到 §2 的某条卡点 | 编号可追 |
| 4 | 所有【推断】原样带标注，未被升级为事实 | 搜【推断】 |
| 5 | 未决与风险单列，且写明「缺它会卡住哪一章」 | 逐条检查 |
| 6 | 用户已确认报告 | 无确认不进 S4 |

**⛔ 本阶段不做什么**：

- 不写 PRD 条款（R/F/AC 编号一个都不出现），只写候选与判断。
- 不编数字。查不到写「未核实」，⛔ 不用「约」「大概」糊过去。
- 不把 S2 的回答直接当事实——回答是人的记忆，事实是文件和命令。
- 不做对标结论（那是 PRD §3 的活，本阶段只留清单）。

## 二、操作步骤

1. **列调查清单**。把 PRD 会涉及的实体全部列出来：既有目录、既有脚本、既有文档、既有数据、既有角色。⛔ 不凭印象列，先在磁盘上 `ls` 一遍。
2. **逐项实测**。每条给「路径 + 实测数字 + 测量方式」三件套。示例：
   - `<项目>/src/` 下 `.py` 文件数：`find . -name "*.py" | wc -l` → 实测 42 个。
   - 既有方案文档：`docs/方案_v1.0.md` 存在，行数见 `wc -l`。
3. **标来源等级**。每条事实标 `实测` / `文档记载` / `用户口述` / `【推断】`。四类不得混用；`用户口述` 与实测冲突时，以实测为准并在报告里写冲突。
4. **摸清底数（三问）**：
   - 已有什么：能直接复用的模块/脚本/文档，写清可复用程度（直接用 / 改改能用 / 只能参考）。
   - 缺什么：从"要达成目标还差什么"反推，逐条写。
   - 多少：数量、体积、覆盖率、当前基线（如"现有 3 个平台适配，缺 2 个"）。
5. **回填问题**。把 S2 的回答逐条抄进「问题回填」表，并在旁标「与实测一致 / 有冲突 / 无法验证」。
6. **出需求候选**。每条候选写四样：候选需求一句话、挂哪个卡点、影响谁、初判优先级（P0/P1/P2）。⛔ 此时不写"为谁做/解决什么问题/带来什么价值"三行，那是 S4 的正式字段。
7. **列未决与待对标**。未决项写「缺它会卡住哪一章」；待对标项写「对标的品类/产品名」。
8. **交确认**。报告发出后等用户确认；确认前 ⛔ 不动 PRD。

## 四、反例

**反例 1：数字没有出处**

```
现有代码量约 8000 行，功能基本齐全，只差调度。
```

错在哪：「约」和「基本」在 S3 就是不合格。PRD §2 要引用这些数字，一旦被追问出处就整章作废。正确：「`find . -name "*.py" -exec wc -l {} +` 合计 7842 行（2026-10-25 实测）」。

**反例 2：把用户口述当事实**

```
Q-04 用户说有定时任务 → 报告 §1 写「已有定时调度」。
```

错在哪：口述是记忆，实测是事实。这条一旦进 PRD §2，施工方会去找一个不存在的模块。正确：标「用户口述」，另起一行写实测结果，冲突单列。

**反例 3：提前写条款**

```
R-01 为运营做批量导入，解决手工复制耗时问题，价值是提效 80%。
```

错在哪：这是 S4 的正式字段。S3 就写成条款形态，等于把未经确认的"提效 80%"焊进 PRD，而它此刻只是推断。

**反例 4：只写结论不写底数**

```
结论：建议本期做导入功能。
```

错在哪：没有"已有什么/缺什么/多少"，S4 写需求时无处可挂，只能凭感觉编价值。S3 的全部价值就在这三项量化。

## 五、衔接条件

**进入 S4 的条件**：

1. 判据 6 条全过，用户已确认报告（口头确认也算，但要在这里写一句"已于 x 日确认"）。
2. §2 三项量化齐全，每个数字可回查。
3. 需求候选已定 P0/P1/P2 初判，P0 条目数量与用户确认的本期范围一致。

**交接物**：报告全文。S4 写 PRD 时：§2 直接引用报告 §1/§2，§4 引用候选表，§3 引用待对标清单，§14 引用未决表。⛔ 不重新发明。

**回退条件**：S4 写「解决什么问题」时发现挂不上任何卡点 → 退回 S3 补 §2.2 缺口，⛔ 不在 PRD 里现编卡点。
