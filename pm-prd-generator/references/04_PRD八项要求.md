## 二、八条逐条的可核形态

### 1) R 条目三行字段（C2）

可核形态：每条 `R-xx` 下方必须出现三行，字段名前缀固定，且内容不是空话。

```markdown
### R-01 批量导入草稿

- 为谁做：运营（每天手动复制 30 篇的那位）
- 解决什么问题：§2 卡点 2「手工复制易漏、单篇 3 分钟」
- 带来什么价值：单篇 3 分钟 → 20 秒，漏发率归零（可观察：AC-01 / AC-02）
- 验收指向：AC-01、AC-02
```

判过线：三行齐；「为谁做」是角色不是「用户」；「解决什么问题」挂到 S3 的卡点编号；「带来什么价值」有可观察量｜判不过：三行缺一；价值写「提升效率」；问题与卡点无关（现编）。

### 2) F 条目五要素（C3）

可核形态：每个 `F-xx` 一张五要素表（竖排两列），五要素名固定。

```markdown
### F-01 导入按钮

| 要素 | 内容 |
|---|---|
| 触发条件 | 点击「开始导入」按钮 |
| 前置条件 | 已登录且剪贴板非空 |
| 展示内容 | 主操作绿底白字按钮，文案「开始导入」；空态文案「剪贴板里没有链接」 |
| 操作规则 | 单次 ≤50 条；运行期禁止改配置 |
| 系统反馈 | 成功：「已导入 N 条」；失败：「第 3 条失败：链接无效」，落日志与列表标记 |
```

判过线：五要素齐；触发条件点到具体操作（有按钮名/事件名）｜判不过：触发条件写「用户操作时」；系统反馈只写「提示成功」（无文案要点、无落点）。

### 3) AC「给定 / 当 / 那么」（C5）

可核形态：一条 AC 一件事，三段各一行，段首词固定。

```markdown
AC-01 【功能点 F-01】
  给定【已登录，剪贴板内有 1 条有效链接】
  当【点击「开始导入」】
  那么【列表新增 1 行，顶部提示「已导入 1 条」】
```

判过线：三段齐；「那么」是可观察结果（界面/文件/退出码/文案）｜判不过：写成「那么【功能正常】」；一条 AC 里塞两个动作（既导入又导出）。

### 4) 状态流转表（C6）

可核形态：五列表格，必须有初态与终态，状态名与流程图逐字一致。

```markdown
| 状态名 | 进入条件 | 退出条件 | 本态允许动作 | 负责人 |
|---|---|---|---|---|
| 待导入（初态） | 新建任务 | 提交成功 | 编辑、删除 | 运营 |
| 已完成（终态） | 全部条目导入成功 | — | 查看 | 运营 |
```

判过线：有初态与终态标记；每个状态有进入与退出条件｜判不过：只有"正常/异常"两态；状态名与 §10 图上的字不一致。

### 5) 业务流程图（C7）

可核形态：§10 有一张 SVG（画法照规范 §四），**异常分支用红虚线画出**，图下配文字版流程说明。

```markdown
## 10. 业务流程图

<svg viewBox="0 0 1080 320">…正常节点 #e8f8ef / 判断节点 #fff7e6 / 异常节点 #ffece8…</svg>

流程说明：开始 → 校验登录 → 逐条导入 → 结束；异常分支：登录失效 → 提示重登（红虚线）；单条失败 → 记入失败清单继续。
```

判过线：图存在（SVG 或文字版流程说明 ≥3 步）；有异常分支｜判不过：只有 happy path；图是截图/外链，无法嵌入 HTML。

### 6) 本期做什么 / 不做什么（C8）

可核形态：两张清单，「不做什么」≥3 条，每条带一句理由。

```markdown
### 本期做

- 多平台采集（P0）
- 失败清单与重试（P0）

### 本期不做

- 不做自动发布：发布需人工过审，自动发会绕过合规闸门。
- 不做多账号并发：本期只有 1 个运营账号，做了没有收益。
- 不做数据看板：依赖埋点体系，本期无埋点。
```

判过线：≥3 条且各带理由｜判不过：「不做什么」只写"其他后续再说"；理由写"暂不需要"（等于没理由）。

### 7) 五步走留痕表（C1）

可核形态：文档 §0 有一张表，五步**全部有内容**，每步有落点。

```markdown
| 步 | 在本项目的落地 | 落点 |
|---|---|---|
| 1 调查事实 | 实测 42 个脚本、3 个适配器 | 需求分析报告 §1 |
| 2 摸清底数 | 存量 7842 行，缺 2 个平台适配 | 本 PRD §2 |
| 3 对标成熟方案 | 对标采集工具品类（X / Y） | 本 PRD §3 |
| 4 先出方案 | 本 PRD 即方案，需求逐条过判据 | 本 PRD §4~§11 |
| 5 最后执行 | 排期 + AC 验收 | 本 PRD §12 |
```

判过线：五步词齐（调查事实/摸清底数/对标成熟方案/先出方案/最后执行），每步有落点｜判不过：只写「已按五步走执行」一句；某步落点写「—」。

### 8) 异常五类必备（C4）

可核形态：§7 至少覆盖五类，每类一行，列齐「触发条件/系统行为（含文案）/用户可做什么/恢复路径」。

| 必备类别 | 最小合格写法 |
|---|---|
| 空数据 | 列表为空时展示「还没有导入记录」+ 引导按钮，⛔ 不显示空白表格 |
| 权限不足 | 进入即拦截并提示「当前账号无导入权限，请联系管理员」，不展示功能入口 |
| 网络异常 | 断网时按钮置灰并提示「网络已断开，恢复后自动续传」 |
| 重复提交 | 同一条链接 10 秒内重复提交 → 去重并提示「该链接已在队列中」 |
| 操作超时 | 单批 >120 秒 → 提示「已超时，已完成 32/50」，保留已完成部分 |

判过线：五类齐；每类有具体文案要点｜判不过：写「异常统一提示错误」（无分支）；五类只覆盖三类。

## 三、写作禁令（出现即返工）

| 禁词/禁形 | 为什么 | 换成 |
|---|---|---|
| 体验良好 / 流畅 / 友好 | 不可判 | 具体动作耗时、点击次数、提示文案 |
| 尽量快 / 尽快 / 优化性能 | 无可观察量 | 「首屏 ≤800ms」「单批 50 条 ≤30s」 |
| 等等 / 其他 / 类似功能 | 需求边界消失 | 逐条列完，或进「本期不做」 |
| 用户 | 无法定位角色 | 运营 / 决策者 / 评审方 |
| 约 / 大概 / 差不多（配数字） | 数字失去出处 | 实测值 + 测量命令 |

## 四、反例

**反例 1：R 条目只有一句话**

```
R-01 做批量导入，提升效率。
```

错在哪：三行字段全缺，下游无法核「为谁做」，也无法从 S3 找到对应卡点，验收时无从判断做没做成。

**反例 2：F 五要素写成了散文**

```
F-01 用户点击按钮后系统开始导入，导入过程中用户可以看进度，失败会有提示。
```

错在哪：五要素混在一段话里，触发条件、反馈文案、操作规则边界全糊在一起，施工方只能猜；lint 也判不过。

**反例 3：状态表与流程图各写一套**

```
§9 状态：待处理 / 处理中 / 完成
§10 图上：未开始 / 进行中 / 已结束
```

错在哪：同一台状态机两套命名，施工方无法判断是不是同一件事，测试用例也对不上号。规范要求逐字一致。

## 五、衔接条件

**进入 S5 的条件**：

1. `python scripts/prd_lint.py <prd.md>` 返回 rc=0（八项形态全过）。
2. 每条 R 的「解决什么问题」都能指回 S3 报告的卡点编号。
3. 每条 AC 都指向具体 F 编号，且该 F 存在。

**交接物**：`PRD_v1.0.md`（纯 LF）。S5 只读它画原型、出 HTML，⛔ 不在 HTML 阶段改需求正文。

**回退条件**：lint 报 C2/C3 缺项且原因是"需求本身没想清"（不是漏写） → 退回 S3 补卡点或退回 S2 补问题，⛔ 不在 S4 现编。
