# PRD 编写规范（本 Skill 内置 · 唯一骨架源）

> 本文件是 `pm-prd-generator` **自带的** PRD 规范，包内自包含，不依赖任何外部文档。
> S4 建骨架、S5 画图、S6 自检全部以本文件为准。
> ⛔ 本包只有这一份骨架；`04_PRD八项要求.md` 只讲「怎么把骨架落成可核形态」，不另立第二套结构。

## 一、文档定位（先想清楚再写）

一份 PRD 同时服务三类读者：

| 读者 | 拿它干什么 | 因此要写什么 |
|---|---|---|
| **决策者** | 拍板做什么 / 不做什么 | 取舍与代价，不写实现细节 |
| **评审方** | 核需求是否站得住 | 为谁做 / 解决什么问题 / 带来什么价值 |
| **施工方** | 照功能点与验收标准干活 | 可测的功能点五要素 + 可观察的验收标准 |

每条内容都要能回答那三问。回答不了的段落，删掉。

### 1.1 事实与推断分离

| 内容类型 | 怎么写 | ⛔ 不许 |
|---|---|---|
| 实测事实 | 写数字 + 出处（文件路径或命令） | 写「大约」「估计」 |
| 推断 | 显式标 **【推断】** | 把推断写成事实 |
| 方案判断（价值、优先级） | 不必标推断，但**必须有依据** | 凭空排序 |
| 查不到 | 写「未核实」 | 编造数字、日期、人名 |

> 这条不是洁癖。PRD 里一个没出处的数字，后面会变成排期、变成验收标准、变成互相指责的依据。

### 1.2 项目管理五步走（每份 PRD 必须留痕）

PRD 头部设「五步留痕」表，五步全部有内容。五步是：

| 步 | 动作 | 硬要求 | 判据 |
|---|---|---|---|
| **1 调查事实** | 先查现状，不凭印象下手 | ⛔ 禁「来了就做」；⛔ 禁先定方案后找依据 | 给出**实测数字 / 路径** |
| **2 摸清底数** | 盘既有机制与存量 | 先查既有件，⛔ 禁重复造轮子 | 「已有什么 / 缺什么 / 存量多少」量化 |
| **3 对标成熟方案** | 先看业界怎么做 | ⛔ 禁拍脑袋自创 | 对标结论 + **映射到自己这边** |
| **4 先出方案** | 出方案不执行 | 附**依据四问**；不可逆项单列待裁 | 获认可后才动手 |
| **5 最后执行** | 按序做 + 自测 | 判据须反向验证「真抓」而非崩溃假抓 | 自测全绿 + 变异全中 |

**为什么五步而不是直接写**：跳过 1~4 直接产出，最常见的三个后果是——造了已有的重复件、写了规范却没落地、把猜测当事实写进文档。三者都不是「写得不够好」，是**方向错了**，返工成本最高。

**依据四问**（第 4 步的附件，任何方案都适用）：

| # | 问什么 | 写法要求 | ⛔ 反面写法 |
|---|---|---|---|
| 1 | 这是一个什么问题？ | 给**归类名 + 一句话定性**，让人不看上下文也知道是哪类事 | 直接从结论开头：「建议分档。」 |
| 2 | 产生原因是什么？ | 讲**机制**（为什么会走到这一步） | 罗列时间线、复述经过、甩锅 |
| 3 | 有哪些影响？ | 说清后果落在谁身上、是「堵住」还是「放错」，**含不做的代价** | 只写「有风险」；只说好处不说代价 |
| 4 | 推荐怎么做？ | 给**明确倾向 + 理由**，理由挂到第 2 或第 3 条上 | 「都行」「看情况」「你定」（= 没给推荐） |

四问缺项时必须显式写「此项无」+ 为什么无，⛔ 不许静默跳过。
第 4 问允许多方案并列（甲 / 乙），但**必须标出推荐哪个 + 为什么**。

**另加一问**：**这次我拒绝做什么？** ——多数事故不是做错了什么，是做了不该做的。

## 二、Markdown 章节结构（顺序固定，编号固定）

```
# <项目名> 产品需求文档（PRD）v1.0
> 文档信息块：版本 / 日期 / 状态 / 依据 / 编写规范

## 0. 五步留痕与文档信息
## 1. 一句话定位与目标用户
## 2. 现状盘点（摸清底数）
## 3. 对标与映射（业界怎么做 → 我们怎么落）
## 4. 需求总览与优先级
## 5. 需求明细（R-xx，逐条：为谁做/解决什么问题/带来什么价值）
## 6. 功能点规格（F-xx，逐功能：触发条件/前置条件/展示内容/操作规则/系统反馈）
## 7. 异常流程与边界场景（E-xx，单独成章）
## 8. 验收标准（AC-xx，给定【条件】、当【动作】时、那么【预期结果】）
## 9. 状态流转表
## 10. 业务流程图（SVG，含异常分支）
## 11. 本期做什么 / 不做什么
## 12. 排期与验收安排
## 13. 原型图（SVG）
## 14. 风险与未决问题
```

### 各章填写要求

**§1 一句话定位与目标用户**：一句话说清「这是什么、给谁、替代什么」。目标用户分**主用户 / 次用户**（次用户如：管理员、其他系统的调用方）。

**§2 现状盘点**：表格。列：模块 / 目录 / 现状（已实现·部分实现·骨架）/ 关键证据（路径 + 实测数字）/ 卡点。数字必须来自实测，注明测量命令或出处。

**§3 对标与映射**：表格。列：业界范式（**点名**：如看板式、表格式、Git 式状态机、CI 流水线式门禁）/ 其核心思想 / 我们映射到什么 / 不适用的部分（为什么）。⛔ 不许写「对标某大厂」这种空话——必须落到可指名的产品或公开方法论。

**§4 需求总览与优先级**：表格。列：需求编号 / 名称 / 优先级（P0 本期必做·P1 本期尽量·P2 下期）/ 一句话价值 / 关联功能点。**优先级判据写在表下**（三条示例：堵不堵主链路 / 新用户新场景少不少卡点 / 安全与合规）。⛔ 优先级不能只凭感觉排，判据要能被别人复核。

**§5 需求明细（R-xx）**：每条需求一张小卡，四行：
- **为谁做**：具体到角色（如「运营」「审核方」「外部集成方」），不写「用户」。
- **解决什么问题**：现状的什么痛（挂到 §2 的某条卡点）。
- **带来什么价值**：可观察的结果（时间 / 错误率 / 卡点减少）。
- **验收指向**：关联的 AC 编号。

**§6 功能点规格（F-xx）**：每个功能点一张五要素表（竖排两列）：

| 要素 | 内容 |
|---|---|
| 触发条件 | 什么操作 / 什么事件起点名（如「点击『开始导入』按钮」「收到派单事件」） |
| 前置条件 | 必须满足什么才允许进入（如「设备已连接且授权」） |
| 展示内容 | 界面上出现什么（控件、文案、**空态文案原文**） |
| 操作规则 | 允许做什么、校验规则、禁则（如「运行期禁止改配置」） |
| 系统反馈 | 成功 / 失败 / 进行中各自的反馈形态（文案要点 + 落点：界面 / 日志 / 文件） |

**§7 异常流程与边界场景（E-xx）**：表格，**至少覆盖五类**（空数据 / 权限不足 / 网络异常 / 重复提交 / 操作超时），再加本项目特有异常。列：编号 / 场景 / 触发条件 / 系统行为（含文案要点）/ 用户可做什么 / 恢复路径。

**§8 验收标准（AC-xx）**：格式硬性——

```
AC-01 【功能点 F-01】
  给定【<前置状态，可测量>】
  当【<动作，单一>】
  那么【<可观察结果：界面 / 文件 / 退出码 / 文案>】
```

一条 AC 只测一件事；结果必须可观察（⛔ 禁「体验良好」这类不可判词）。

**§9 状态流转表**：列：状态名 / 进入条件 / 退出条件 / 本态允许动作 / 负责人（角色）。状态机必须有初态与终态；表格（§9）与图（§10）**状态名逐字一致**。

**§10 业务流程图**：SVG（画法见 §四）。主线横向或纵向，**异常分支必须画**（红虚线），旁注判据。图下配「流程说明」文字版（给看不了图的人）。

**§11 本期做什么 / 不做什么**：两张清单。「不做什么」每条给一句理由。

**§12 排期与验收安排**：表格，四字段：改什么（指到文件 / 模块）/ 交给谁（角色）/ 何时验收（日期，晚于登记日）/ 谁验收（**≠ 交给谁**）。日期未定的写「待定」并说明原因。

**§13 原型图**：SVG（画法见 §五）。桌面工具按界面骨架画；Web / 文档类按信息架构画框架图即可。

**§14 风险与未决**：表格。列：风险 / 影响 / 缓释 / **是否需决策者裁量**。⛔ 未决项不许藏在正文里。

## 三、按项目类型适配（写前先定位自己属于哪类）

同一套骨架，不同类型的项目侧重完全不同。**写之前先选定类型**，再决定 §2 / §7 / §14 的深浅：

| 项目类型 | PRD 侧重 | 特别注意 |
|---|---|---|
| **容器型（多子项目编排）** | 容器级需求 + 子项目分工边界 + 任务流转 | 需求落在「编排与边界」而非某个子工具的功能细节；每个子项目一节现状 |
| **从 0 到 1 的新产品** | 完整链路需求 + 与既有方案的差异化 | 存量极少，现状章如实写「几乎没有存量」，别假装有 |
| **工具型（单机 / 设备侧）** | 能力边界 + 平台扩展性 | 明确「工具不做业务决策」的边界；各平台支持现状如实写 |
| **安全 / 清理类工具** | **安全边界即第一需求** | 异常流程与权限是重点；破坏性操作的硬坑必须进风险章 |
| **治理 / 平台型** | 规范体系 + 硬闸门机制 | 它本身是「管其他项目的项目」，PRD 要写清规范生命周期与落地核查机制 |
| **存量改造 / 改版** | 现状盘点 + 兼容与迁移 | §2 要写「改前是什么样」，§7 要覆盖迁移过程的中间态 |

## 四、SVG 业务流程图规范

- 画布 `viewBox="0 0 1080 高"`，横向主线（左 → 右），异常分支向下。
- 节点：圆角矩形 `rx=8`；正常节点填充 `#e8f8ef` 边 `#07c160`；人工判断节点填充 `#fff7e6` 边 `#fa8c16`（菱形也可）；异常节点填充 `#ffece8` 边 `#e64340`；终态双边框。
- 箭头：主线 `#333` 实线 1.5px 带箭头标记；异常 `#e64340` 虚线 `stroke-dasharray="5 4"`。
- 文字：12px `Microsoft YaHei`，`#333`；节点内文字不超过 12 字 / 行，可两行。
- 每个节点左上角标编号（与状态表 / AC 编号对应）。
- 图例放右下角：四种节点色 + 两种线型。
- **必须有文字版流程说明**（图下）。

## 五、SVG 原型图规范

**桌面 GUI 类**：

- 窗口按 1280×780 比例缩放。
- **顶部大标题条**：主色 `#07c160` 填充，白字 14 bold。
- **Tab 条**：tab 文案两端留空格（视觉更稳），当前 tab 白底。
- 页内工具条：次按钮灰底 `#e9e9e9`、主操作绿底白字、危险操作红底白字，一律 `bd=0` 扁平直角。
- 内容区：白卡包裹表格（表头 `#fafafa`，行高 34 等比），表格线 `#eee`。
- 文字层级：主文字 `#333`、次要 `#666`、禁用 `#999999`。
- 每个原型图下配「原型说明」：标出与 F-xx 的对应关系。

**Web / 文档类**：按信息架构画框架图（导航区 / 主内容区 / 操作区），标注每块的用途，不必画到控件级。

⛔ 原型图上不许出现 PRD 没写的按钮或字段——那等于在图上偷偷加需求。

## 六、HTML 交付规范

- **单文件自包含**：内联 `<style>`，⛔ 不引外部 CSS / JS / CDN；SVG 内嵌。
- 编码 UTF-8，`<html lang="zh-CN">`。
- 布局：顶部文档头（标题 + 元信息 chips）→ 左侧 sticky 目录（h2 自动生成不了就手写锚点）→ 右主内容 `max-width: 960px`。
- 组件：章节卡（白底圆角 10、轻阴影）、表格（斑马纹 `#fafafa`）、AC 块（左边框 4px 绿，「给定 / 当 / 那么」三行各带标签 chip）、需求卡（左绿边）、异常表（场景列红字标签）、状态表（状态列彩色 chip）、原型图（SVG 居中 + 说明）。
- 配色：主色 `#07c160`、危险 `#e64340`、警示 `#fa8c16`、纸底 `#f5f6f7`、白卡 `#fff`、主文字 `#333`、次要 `#666`、线 `#e8e8e8`。
- 页脚：文档信息 + 「本文档按 PRD 编写规范产出」。
- 建议命名：`<项目名>_PRD_v1.0.md` / `<项目名>_PRD_v1.0.html` / `<项目名>_原型.html`。
- **写盘纪律**：MD / HTML 均为**纯 LF**，用 Python `write_bytes(...)` 或 `write_text(..., newline="\n")`，⛔ 不用默认 `write_text`。

> 为什么强调纯 LF：同一份文件在 Windows 编辑器里保存会变成 CRLF，之后 diff 全变、脚本里按字节比对全错，排查一次要花掉半天——成本极低、收益确定。

## 七、质量自检（交稿前逐条过，逐条填「过 / 不过 + 证据」）

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 五步留痕 | 五格全满；「不做什么」≥3 条且各带理由 |
| 2 | 需求三问 | 每条 R 有「为谁做 / 解决什么问题 / 带来什么价值」，缺一即返工 |
| 3 | 功能点五要素 | 每个 F 五要素齐，触发条件点名到具体操作（⛔ 禁「用户操作时」） |
| 4 | 异常五类 | E 章覆盖空数据 / 权限不足 / 网络异常 / 重复提交 / 操作超时 |
| 5 | 验收格式 | AC 全部「给定 / 当 / 那么」三段，结果可观察 |
| 6 | 状态一致 | 状态表与流程图状态名逐字一致 |
| 7 | 数字有出处 | 每个数字有出处；【推断】标注保留 |
| 8 | HTML 自包含 | 单文件可离线打开；SVG 无外部引用；`grep -cE '<link|src=|@import'` = 0 |
| 9 | 排期四字段 | 四字段齐，且「谁验收 ≠ 交给谁」 |
| 10 | 交付说明 | 含交付物清单、判据结果、已知缺陷、未决项、下一步交给谁 |

> 第 10 条容易被跳过。没有交付说明的 PRD，接收方只能自己重新判断一遍哪些地方还没定——等于把 S6 的工作推给了别人。
