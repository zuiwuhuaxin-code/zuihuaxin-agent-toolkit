# quality-dev-management

把「拿到一份 PRD 之后，如何写到能被独立审查通过」这件事，固化成八个串行阶段。每个阶段有独立说明文档、独立判据、独立禁止项；跨阶段只有一条硬规矩——**上一阶段的产物是下一阶段的唯一输入，不许跳步、不许合并**。

## 一、三条贯穿全 Skill 的硬规矩

违反任意一条，本阶段不算完成，⛔ 不许进入下一阶段。

**H1 产物必须可核。**
每个阶段产出都要有机器可判或人可查的证据：`rc`、退出码、文件是否真在盘上、行数、哈希变化、报告里的 `file:line`。⛔ 不许「口头声称已完成」——「我已自测通过」不是证据，`python -m pytest → rc=0` 才是；「已按报告整改」不是证据，整改对照表逐条挂到 `报告行号 → 改后 file:line` 才是。

**H2 反向变异必带对照组（`00_工程规范.md` §四）。**
反向变异红了，要能证明「是判据抓到的」，不是环境坏了、依赖没定位、脚本自己崩了。做法：同环境、同数据跑两遍——改坏的那遍必须红，不改的那遍必须绿。缺对照组 = 无法区分「真抓」与「假红」，判据形同未验。

**H3 审查方 ≠ 施工方（`00_工程规范.md` §六）。**
独立审查必须换身份、只读：不写一个字节的源码，只出报告。自审、同一角色再检查一遍、施工方中途参与的「复审」，都不算独立审查。⛔ 不许拿「验收」当「已过审」——`已完成` = 独立审查通过 **且** 验收通过，缺一不可。

> 三条规矩的出处：本包 `00_工程规范.md` §四（反向变异带对照组）/ §六（审查方≠施工方）。
> 以上条款的完整定义（含判据、反例、边界）见本包 `references/00_工程规范.md`。
> 两处冲突时**以它为准**，并顺手把本文件改一致 —— ⛔ 不许让两份说法并存。

## 二、rc 四档语义（验收标准一律用它表达）

唯一源：本包 `00_工程规范.md` §三「rc 四档」。本 Skill 只沿用，不另造。

| rc | 语义 | 判定（能回答「谁错了」） |
|---|---|---|
| 0 | 干净 / 全过 | 判据跑完了，结论是没问题 |
| 1 | 检出 | 判据跑完了，确实有东西该拦（业务问题，归施工方改） |
| 2 | 调用层崩了 | 脚本自己坏：Traceback / 未捕获异常 / 内部不一致 |
| 3 | 判据不可用（报灰） | 闸给不出可信结论：输入缺失损坏、环境缺依赖、用法错 |

三条纪律：判据不可用 ⛔ 绝不返回 0（「没查出来」≠「没问题」）；业务检出必须落 1，⛔ 不写成 2；rc ∈ {2,3} = 没结论，调用方 ⛔ 既不当通过也不当检出。

**验收标准的唯一合法形态是可观察结果**，写法对照：

| ✅ 可观察 | ⛔ 不可观察 |
|---|---|
| `python scripts/acceptance_gate.py ac.json` → rc=0 | 「功能已实现完毕」 |
| `SKILL.md` 存在且行数 ∈ [200,320] | 「文档写得比较完整」 |
| `--selftest` 断言 rc 序列 = 0/1/3 | 「自测都过了」 |
| 变异后 `sha256` 变化且闸 rc=1，对照组 rc=0 | 「反向变异做过了」 |
| 审查报告每条含 `path:line`，`grep -c` 命中数 = 条目数 | 「已逐条审查」 |

## 三、适用与不适用

适用：已有 PRD（或等价需求契约），要把需求变成可验收代码的全过程；存量项目按 PRD 改造；交付前质量收口。

不适用：从需求到 PRD（那是 `pm-prd-generator` 的活）、纯技术选型调研、UI 视觉设计、真实渗透测试。

**两边的接口契约**：本 Skill 只读 `PRD_v<x>.md`，⛔ 不改一个字。发现 PRD 缺陷 → 写进 S1 的冲突清单退回产品侧或提建议，⛔ 不许在施工中私改需求。

## 四、八阶段总览

```
S1 项目评估 → S2 施工计划 → S3 编码与自测 → S4 红队攻防 → S5 蓝队防守
                                                        → S6 独立审查 → S7 闭环完善 → S8 源码汇总
```

| 阶段 | 名称 | 核心动作 | 产出 | 说明文档 |
|---|---|---|---|---|
| S1 | 项目评估 | CODE 视角评估可行性 + **指出 PRD 与现状的冲突** | 评估报告 + 冲突清单 | `references/01_项目评估.md` |
| S2 | 施工计划 | 拆任务 / 定顺序 / 定验收点 / 定回滚点 | 施工计划 | `references/02_施工计划.md` |
| S3 | 编码与自测 | 按计划编码 + 正/反/边界自测 + **反向变异带对照组** | 代码 + 自测记录 | `references/03_编码与自测.md` |
| S4 | 红队攻防 | 攻击路径 + G/E/A/I/F 五列对照 + 自行加固 + 多轮 | 红队报告 | `references/04_红队攻防.md` |
| S5 | 蓝队防守 | 事前防御 / 事中阻断 / 事后追溯 三段全链路 | 防御报告 | `references/05_蓝队防守.md` |
| S6 | 独立审查 | 换身份只读审 → 先读 PRD → 验收标准 + 测试用例 + 审查报告 | 审查报告 | `references/06_独立审查.md` |
| S7 | 闭环完善 | 以审查报告为唯一整改依据 → 整改 → 自测 → 反向变异 → 符合验收规范 | 终版代码 + 整改对照 | `references/07_闭环完善.md` |
| S8 | 源码汇总 | 全部源码 → 单文件可读 HTML（目录树 + 跳转 + 行号 + 高亮） | 源码.html | `references/08_源码汇总HTML.md` |

**四道闸，过不了不许进下一阶段**：

| 闸 | 位置 | 判据 | 不过怎么办 |
|---|---|---|---|
| 闸一 | S1 → S2 | 冲突清单每条有「冲突证据 + 建议 + 归属（改 PRD / 改实现）」 | 缺归属的退回，⛔ 不带未决冲突开工 |
| 闸二 | S2 → S3 | 每个任务有验收点 + 回滚点，且验收点能用 rc/文件/行数表达 | 补可观察判据 |
| 闸三 | S3 → S4 | 自测正/反/边界三面齐 + 反向变异有一对「红/绿」记录 | 补对照组，⛔ 只红不绿不算 |
| 闸四 | S6 → S7 | 审查报告含验收标准 + 测试用例 + 三级分类条目，每条带 `file:line` | 报告不合格退回重审 |

S7 出关判据另算：`acceptance_gate.py` rc=0 且整改对照表无「未整改」行。

## 五、S1 项目评估

- **输入**：`PRD_v<x>.md`（只读）+ 现有代码库路径 + 运行环境。
- **动作**：
  1. 按 `00_工程规范.md` §一「执行五步」的前两步走：**调查事实**（读 PRD、读现状代码、跑一次现状基线，给实测数字与路径）+ **摸清底数**（已有能力 / 缺失能力 / 存量多少，量化）。
  2. 逐条把 PRD 要求映射到「现状能做到 / 要改 / 做不到」，每条标影响面。
  3. **写冲突清单**：PRD 与现状打架的地方逐条列，⛔ 不许照单全收。
  4. 给可行性结论 + 三种以上路径（不止二选一），标代价与推荐；每条建议按 `00_工程规范.md` §二 附**依据四问**（什么问题 / 产生原因 / 影响 / 推荐怎么做）。
- **产出**：评估报告（含现状基线数字）+ 冲突清单（每条挂建议与归属）。
- **⛔ 本阶段不做什么**：不改 PRD；不写一行业务代码；不做详细排期（那是 S2）；不把「我觉得能做」当评估结论。
- **完成判据**：冲突清单每条有 `PRD 行号 + 现状 file:line + 建议`；现状基线有实测数字；用户/产品侧已对冲突给出裁决。
- **读**：`references/01_项目评估.md`。

## 六、S2 施工计划

- **输入**：已裁决的冲突清单 + 评估报告。
- **动作**：
  1. 拆任务到「一次能做完、能单独验」的粒度，每任务 ≤ 半天量级，超了就再拆。
  2. 定顺序：先打地基（数据/契约/接口）后做表现层；有依赖的显式写前置任务编号。
  3. 每题写**验收点**（可观察结果）、**回滚点**（改坏了怎么退回去）、**影响文件**。
  4. 标出「本期不做」，防止范围蔓延。
- **产出**：施工计划（任务表 + 依赖图 + 验收点 + 回滚点）。
- **⛔ 本阶段不做什么**：不开始编码；不写「预计 X 小时」这类不可核估算；不把任务拆成「做登录」这种一天以上的大块；不省略回滚点。
- **完成判据**：每个任务四要素齐（验收点 / 回滚点 / 影响文件 / 前置任务）；验收点全部可观察；无孤立任务（依赖图连通）。
- **读**：`references/02_施工计划.md`。

## 七、S3 编码与自测

- **输入**：施工计划 + 冲突裁决结论。
- **动作**：
  1. 按计划顺序编码，一任务一提交（或一任务一变更集），提交信息挂任务编号。
  2. 自测必须三面齐：**正例**（正常路径）、**反例**（该被拦住/该报错的输入）、**边界**（空、0、超长、并发、权限不足）。
  3. **反向变异**：对每条关键判据，故意改坏被测代码或判据本身，确认闸变红；同时跑**对照组**（不改坏），确认仍绿。
  4. 把自测与变异结果落成表：变异什么 / 期望怎么红 / 实际 rc / 对照组 rc。
- **产出**：代码 + 自测记录 + 反向变异记录（含对照组）。
- **⛔ 本阶段不做什么**：不用「跑通了」代替断言；不写只测正常路径的用例；不在反向变异里只跑红的那一半；不为了让闸变绿而放宽判据（那是拆闸）。
- **完成判据**：三面用例齐且全绿；每条变异有「变异点 / 期望红 / 实测 rc=1 / 对照组 rc=0」四列；`py_compile` 或等价语法检查 rc=0。
- **读**：`references/03_编码与自测.md`。

## 八、S4 红队攻防

- **输入**：S3 的代码与自测记录。
- **动作**：
  1. 换红方身份，按攻击面清单逐面扫（认证授权 / 输入校验 / 密钥凭证 / 文件路径 / 越权 / 日志泄露 / 依赖供应链 / 配置错误）。
  2. 每条缺口填 **G/E/A/I/F 五列**：G 对应哪道闸门、E 缺口编号、A 攻击路径、I 影响、F 加固措施。
  3. 自行加固，加固后再攻一轮；**多轮递增**，每轮针对上一轮加固后的**新**缺口，⛔ 不许把上一轮的缺口重抄一遍充数。
  4. 收口时按 `block → warn → ⛔ 禁 silent-off` 给每道闸定档（`00_工程规范.md` §七）。
- **产出**：红队报告（五列对照表 + 轮次记录 + 加固清单）。
- **⛔ 本阶段不做什么**：不写「可能存在 SQL 注入」这种无编号无位置的结论；不替代 SAST/DAST 工具；不对生产环境发起任何真实攻击；不止于「列概念」。
- **完成判据**：每个攻击面至少一条记录或显式写「本面无缺口 + 判据」；缺口编号唯一且连续；每条有对应 F 加固；轮次表能看出「本轮新增缺口来自上轮哪条加固」。
- **读**：`references/04_红队攻防.md`。

## 九、S5 蓝队防守

- **输入**：红队报告 + 加固后的代码。
- **动作**：
  1. 按**事前 / 事中 / 事后**三段写全链路：事前（预防机制）、事中（阻断与告警）、事后（追溯与取证）。
  2. 每段回答三问：防什么（对应哪条 E）、用什么机制（落到文件与函数）、怎么证（rc / 日志字段 / 用例）。
  3. 闸门分层直接引`00_工程规范.md` §七的四层（pre-commit / pre-receive / CI required / artifact scan）与置信度降级，⛔ 不另造一套闸门模型。
  4. 每道闸写清「关不掉 / 可关但有告警」，⛔ 不许出现 silent-off。
- **产出**：防御报告（三段 × 三问矩阵）+ 源码指针。
- **⛔ 本阶段不做什么**：不把「加了 try/except」当防御机制；不宣称服务端已把守（未实测配置不许说）；不写只有事中一段的残缺链路。
- **完成判据**：三段齐全，每段每条机制挂 `file:line`；每条 E 至少被一段覆盖或有「不覆盖 + 理由」；无 silent-off。
- **读**：`references/05_蓝队防守.md`。

## 十、S6 独立审查

- **输入**：PRD（**必须先读**）+ 全部源码 + 红蓝报告。
- **动作**：
  1. **换身份**：以独立审查方身份进入，只读，⛔ 不改任何源码与配置。
  2. **先读 PRD**，从 PRD 反推验收标准（每条可观察）与测试用例（正/反/边界）。
  3. 按 `00_工程规范.md` §六 代码审查铁律输出：🔴Blocker / 🟡Suggestion / 💭Nit 三级；每条含 `真实 file:line + 代码片段 + 触发条件与后果 + 可落地修法`。
  4. 末尾给修复优先级与「能否验收」结论。
- **产出**：审查报告（验收标准 + 测试用例 + 三级条目 + 结论）。
- **⛔ 本阶段不做什么**：不修代码（哪怕一行）；不编造行号或代码片段；不用「建议优化」这种不可落地的措辞；不做自审替代。
- **完成判据**：报告先出现「依据 PRD 的验收标准」章节；每条条目有真实 `file:line` 且回读能对上；`git status` 证明零改动。
- **读**：`references/06_独立审查.md`。

## 十一、S7 闭环完善

- **输入**：审查报告（**唯一整改依据**）。
- **动作**：
  1. 把报告条目逐条转成整改任务，建对照表：`报告行号 → 条目 → 改法 → 改后 file:line → 验证方式`。
  2. 只改报告点到的，⛔ 不顺手重构（顺手改会引入报告未覆盖的盲区）。
  3. 整改后重跑自测 + 反向变异（仍带对照组）。
  4. 跑 `acceptance_gate.py` 出 rc；rc≠0 继续改，直到 rc=0。
- **产出**：终版代码 + 整改对照表 + 验收闸门 rc 记录。
- **⛔ 本阶段不做什么**：不整篇重写（只重做有问题的部分）；不把「改不了」写成「已评估影响可接受」；不在对照表里留空行。
- **完成判据**：对照表无「未整改」；`acceptance_gate.py` rc=0；整改处均有对应自测用例。
- **读**：`references/07_闭环完善.md`。

## 十二、S8 源码汇总 HTML

- **输入**：终版代码目录（S7 之后）。
- **动作**：
  1. 跑 `python scripts/source_pack.py <源码目录> -o 源码.html`。
  2. 打开验证：左侧目录树可折叠、点文件名能跳到源码、每行有行号、关键字有高亮、断网可看。
  3. 在交付说明里写清「打包了哪些扩展名、排除了哪些目录、文件数与总行数」。
- **产出**：单文件 `源码.html`。
- **⛔ 本阶段不做什么**：不引外部 JS/CSS/CDN；不打包 `__pycache__` / `.git` / 二进制；不在 HTML 里改源码内容。
- **完成判据**：`grep -cE '<script|<link|src=|@import'` = 0；页面统计注释 `source_pack: files=N` 与源码目录实有文件数一致；断网能开且跳转有效。
- **读**：`references/08_源码汇总HTML.md`。

## 十三、脚本

两个脚本均零依赖（仅标准库），全部中文输出，纯 LF 写盘，rc 四档语义。

### acceptance_gate.py —— 验收闸门

```bash
python scripts/acceptance_gate.py <验收清单.json>     # 0 全过 / 1 有未过项 / 3 判据不可用
python scripts/acceptance_gate.py --example           # 打印清单模板
python scripts/acceptance_gate.py --selftest          # 断言 合格/故意失败/损坏/子命令崩溃 → rc 0/1/3/3
```

清单是 JSON，`items` 每项一个检查，支持五类：

| type | 必填字段 | 判据 |
|---|---|---|
| `file_exists` | `path` | 文件存在且非 0 字节 |
| `file_absent` | `path` | 文件不存在（用于反向验收） |
| `file_contains` | `path`、`patterns`、可选 `min_hits`、`regex` | 命中关键词条数 ≥ min_hits |
| `line_count` | `path`、可选 `min`/`max` | 行数落在区间内 |
| `command` | `cmd`（数组）、可选 `expect_rc`、`timeout` | 子进程 rc == expect_rc |

⚠ 子命令返回 rc=2 视为「它自己崩了」，整条判据报灰（rc=3），⛔ 不当成检出。判据不可用优先于检出。

`--selftest` 内置四份清单：合格 → 0、故意失败 → 1、损坏 → 3、子命令崩溃 → 3。

### source_pack.py —— 源码汇总

```bash
python scripts/source_pack.py <源码目录> -o out.html [--ext .py,.md] [--exclude dir1,dir2] [--title 名称]
python scripts/source_pack.py --selftest              # 临时目录造 2 文件，断言 HTML 含文件名/行号/无外链
```

单文件 HTML：`<details>` 原生折叠目录树（无 JS）+ 锚点跳转 + 每行行号 + CSS 类极简高亮。

## 十五、已知局限

- **不替代 SAST / DAST 专业工具。** S4 红蓝攻防是**思维框架 + 报告格式**，产出的是攻击面清单与加固建议，⛔ 不是真实渗透测试结果，也没有任何自动化扫洞能力。需要工具级扫描时明确写「需专项工具，本 Skill 不覆盖」。
- **不保证漏洞被找全。** 攻击面清单是启发式的，红队报告覆盖了八个面也不等于系统安全；零日、业务逻辑漏洞、第三方组件内部缺陷都超纲。
- **不改需求。** S1 只能提冲突与建议，PRD 的裁决权在产品侧；本 Skill 无权重写验收标准来迁就实现。
- **`acceptance_gate.py` 只核「清单写了什么」**，清单本身是否覆盖真实验收点要靠 S6 审查报告兜底——闸绿不等于验收点齐。
- **`source_pack.py` 不处理超大仓库。** 单文件 HTML 会把全部源码塞进一个文件，几万行的仓库会产出几十 MB 页面；这种情况按模块分多次打包。
- **不覆盖部署上线、生产监控、真实压测**，这些需要独立流程。
- 本 Skill 的八阶段源自 通用研发流程的 S1~S8，上游 PRD 生成属 `pm-prd-generator`。
