# S6 自查与交付 —— 十条逐条过，缺项不带出门

> 阶段定位：把「我觉得写完了」换成「十条各有证据」。这一步的唯一产出是**可信度**。
> 上游：`05_原型与HTML交付.md`。下游：需求评审 / `quality-dev-management`（只读本 PRD）。

## 一、目标与判据

**目标**：交付一份"任何第三方照单能核"的 PRD 包：机器能跑的判据全绿，人能读的十条全有证据，未决项明写不隐藏。

**判据（全过才算交付）**：

| # | 判据 | 判定方式 |
|---|---|---|
| 1 | `python scripts/prd_lint.py <prd.md>` rc=0 | 命令退出码 |
| 2 | 质量自检 10 条逐条有「过/不过 + 证据」 | 表内无空格 |
| 3 | 每条证据可回查（命令输出/章节号/文件路径） | 抽 3 条回查 |
| 4 | 未决与风险未被删除，且写明需谁定 | §14 检查 |
| 5 | 交付说明含接收方与下一步 | 文本检查 |

**⛔ 本阶段不做什么**：

- 不把缺项写成「后续补」「下版完善」当交付——缺项要么修，要么降级进"本期不做"并给理由。
- 不用「已自测」替代逐条证据；没有命令输出就是没有证据。
- 不自己宣布"独立审查通过"。独立审查是换身份只读复核，属 `quality-dev-management`，⛔ 自审不算。
- 不在交付时改需求正文——发现要改，退回 S4。

## 二、操作步骤

1. **先跑机器判据**。`python scripts/prd_lint.py <prd.md>`；rc=1 看缺项清单逐条修，rc=3 先解决文件问题（路径/编码/空文件）。
2. **再跑人读十条**。10 条原文见 `00_PRD编写规范.md` §七；本文件只提供「核查方式」和「证据形态」，⛔ 不改判据本身。
3. **逐条填证据**。每条写清"用什么方式核的、核出什么"，例：第 5 条证据写「§8 共 12 条 AC，`grep -c "^AC-"` = 12，逐条含 给定/当/那么：是」。
4. **处理"不过"**。分三类：漏写 → 当场补；需求没想清 → 退回上一阶段并在表里记「退回 Sx」；本期不做 → 移入 §11 并给理由。
5. **重跑 lint**。任何补充后必须重跑，⛔ 不许凭记忆认为已过。
6. **写交付说明**。四段：交付物清单、判据结果、已知缺陷与未决、下一步交给谁。
7. **定接收方**。需求评审（REQ）核需求契合；施工方（CODE）照功能点干活，**只读不改**。
8. **留痕**。把 lint 命令与输出、10 条表一起贴进交付说明，供下一位复核。

## 四、反例

**反例 1：十行全写"通过"**

```
| 1 | 过 | | 2 | 过 | | … | 10 | 过 |
```

错在哪：没有证据的"通过"等于没做。评审无法复核，等于把自检变成了盖章仪式。规范的判据是"逐条可核"，不是"逐条声明"。

**反例 2：缺项写成"后续补"**

```
第 4 条：E 章待补，下版完善。
```

错在哪：E 章缺五类异常，直接导致施工方按 happy path 写代码，异常处理全靠现场发挥。缺项只有三种合法处置：当场补、退回上一阶段、明确移入"本期不做"并给理由。

**反例 3：改完不重跑 lint**

```
（补了 R-03 的三个字段，但没重跑，交付说明仍引用上一次 rc=0 的输出）
```

错在哪：上一次的 rc=0 证明的是旧文件。判据只对"当前文件"有效，任何编辑后必须重跑，并把新输出贴进交付说明。

**反例 4：自己宣布独立审查通过**

```
交付说明：已自查且通过独立审查，可直接施工。
```

错在哪：自查与独立审查是两个身份。审查方必须换身份、只读、逐字核对，属 `quality-dev-management` 的 S6；由产出方自己宣布，正是这条链要防的事。

## 五、衔接条件

**交付成立的条件**：

1. lint rc=0，且交付说明里的输出是**最后一次编辑之后**跑的。
2. 10 条全部有结论 + 证据，无空格、无"待补"。
3. 未决项在 §14 与交付说明里同时存在，需裁量项标了"待决策者定"。
4. 接收方明确：需求评审（REQ）+ 施工方（CODE，只读）。

**交接物**：PRD.md + HTML + 原型.html + 分析报告 + 自检表 + 交付说明。

**回退条件**：

- 评审提出需求级异议 → 退回 S2/S3，⛔ 不在 S6 就地改条款。
- 施工方发现 PRD 有缺陷 → 提回产品侧改，⛔ 施工中私改需求。
- 本 Skill 到此结束；施工、自测、红蓝攻防、独立审查、闭环完善属 `quality-dev-management`。
