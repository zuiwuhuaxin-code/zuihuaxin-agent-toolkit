# S2 施工计划

> 位置：S1 评估报告与冲突裁决之后，编码之前。
> 本阶段唯一不可替代的价值：**把「要做什么」翻译成「按什么顺序做、做完怎么验、做坏怎么退」**。没有回滚点的计划不是计划，是愿望。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 任务拆到可独立验证 | 每个任务的影响文件数 ≤ 5，且能单独跑一条验收命令 |
| 顺序可执行 | 依赖图连通、无环、无孤立任务；每个任务的前置任务编号真实存在 |
| 验收点可观察 | 全部验收点是 rc / 文件存在 / 行数 / sha256 / 字段值，⛔ 无「功能正常」 |
| 回滚点可执行 | 每个任务写清「退回到哪个状态 + 用什么命令/提交」，⛔ 无「删掉重写」 |
| 范围受控 | 有「本期不做」清单，至少 3 条 |

闸二：`acceptance_gate.py` 检查施工计划含「任务表」「本期不做」两节，任务表每行四要素非空。rc=0 才进 S3。

## 二、输入

1. S1 评估报告（尤其冲突清单的裁决结果）。
2. PRD 里全部 `F-xx` 与 `AC-xx`（验收点必须能追溯到它们）。
3. 现有代码的模块边界（决定任务切分线在哪）。

**前置检查**：拿任务编号体系定下来（建议 `T-01` 起），后续提交信息、整改对照表、审查报告都引用它。⛔ 不许中途改编号体系。

## 三、操作步骤

**B1 定切分线**
优先按「变更边界」切，不按「技术分层」切。一个任务应当能独立合并、独立回滚。反例：把「改数据库 + 改接口 + 改前端」拆成三个任务，任何一个单独合并都跑不起来。

**B2 拆任务**
每个任务写到四要素齐：影响文件 / 验收点 / 回滚点 / 前置任务。粒度判据：一个任务写不出「一条能跑的验收命令」就说明还没拆够。

**B3 排顺序**
三条排序原则，冲突时按序号优先：
1. 契约先行：数据结构、接口签名、常量表先定，避免下游反复改。
2. 风险先行：S1 里标「做不到 / 高影响」的先做探针任务（只验可行性，不追求完整），失败早暴露。
3. 依赖收敛：能并行的任务排在一起，串行链越短越好。

**B4 定验收点**
每条验收点必须形如：`<命令/检查> → <期望结果>`。示例：`python -m pytest tests/test_auth.py → rc=0`、`grep -c "def login" src/auth.py → 1`。⛔ 不写「登录功能可用」。

**B5 定回滚点**
每条写三样：回滚目标（回到哪个 commit / 哪个配置值）、回滚动作（命令）、回滚后如何确认（rc / 文件）。数据类变更必须写「迁移是否可逆」，不可逆的要单列并标「需备份」。

**B6 写「本期不做」**
把 PRD 里被裁决为「后续」的、以及自己识别出的范围外诱惑写下来，至少 3 条，每条写「为什么不做」。

**B7 跑闸 → 交计划**

## 四、输出模板

### 4.1 施工计划骨架

```markdown
# 施工计划 · <项目名> · <日期> · 基于 PRD v<x>

## 1 范围
- 覆盖需求：R-01~R-05 / F-01~F-09 / AC-01~AC-11
- 本期不做：见 §5

## 2 任务表
| 编号 | 任务 | 影响文件 | 验收点（命令 → 期望） | 回滚点 | 前置 |
|---|---|---|---|---|---|
| T-01 | 建 auth 表与迁移 | `migrations/001.sql` | `python -m pytest tests/test_migrate.py` → rc=0 | `git revert <sha>`；迁移含 `down` | 无 |
| T-02 | 登录接口 | `src/auth.py`、`src/routes.py` | `python -m pytest tests/test_auth.py` → rc=0 | 回退到 T-01 的 commit；关 `ENABLE_LOGIN` | T-01 |
| T-03 | 前端登录页 | `web/login.html` | 文件存在 + 含 `<form id="login">` → 1 命中 | 删文件（纯新增，无副作用） | T-02 |

## 3 依赖图
```
T-01 → T-02 → T-03
             ↘ T-04（限流，可与 T-03 并行）
```

## 4 验收点汇总（供 acceptance_gate.py 直接消费）
| AC | 对应任务 | 检查方式 | type |
|---|---|---|---|
| AC-01 | T-01 | `migrations/001.sql` 存在 | file_exists |
| AC-02 | T-02 | `tests/test_auth.py` 含 3 个 `def test_` | file_contains |
| AC-03 | T-02 | 跑测试 rc=0 | command |

## 5 本期不做
| # | 不做的事 | 理由 | 谁提出 |
|---|---|---|---|
| N-01 | 第三方 OAuth 登录 | PRD 未列，本期不做 | 施工方 |
| N-02 | 密码强度策略 | 待产品定规则 | 产品侧 |

## 6 风险与探针
| 风险 | 触发条件 | 探针任务 | 探针结论 |
|---|---|---|---|
| 迁移在大表上锁表 | 行数 > 100 万 | T-01a 只跑 explain | <结果> |
```

### 4.2 四要素的空值判据

| 要素 | 空值长什么样 | 判据 |
|---|---|---|
| 影响文件 | 「相关文件」 | 必须是路径，能 `ls` 到或明确是新建 |
| 验收点 | 「功能正常」 | 必须含 `→ rc=` 或 `→ 存在` 或 `→ 命中 n` |
| 回滚点 | 「有问题就回退」 | 必须含具体 commit / 命令 / 配置键 |
| 前置 | 空 | 必须写「无」或真实任务编号 |

## 五、反例

**反例 1：任务粒度按技术分层**
> T-01 改数据库，T-02 改后端，T-03 改前端，三个任务都「验收点：相关测试通过」。

错在哪：任一个单独合并都跑不起来，等于把一次大改拆成三次必然中间态破窗的提交；回滚点也无从谈起（回滚 T-02 会留下 T-01 的表没人用）。切分线应在「变更边界」，而不是「技术层次」。

**反例 2：验收点写成主观判断**
> 「T-02 验收点：登录流程顺畅，无异常。」

错在哪：无法机器判、无法交付审查方复核、S7 无法证「已符合验收规范」。验收点必须是命令加期望值。

**反例 3：回滚点写成「重写」**
> 「回滚点：如出问题，重写该模块。」

错在哪：重写不是回滚，是把故障态扩大。回滚必须是确定性的、能在 1 分钟内执行的动作。

**反例 4：漏「本期不做」**
> 计划里没有不做清单，编码时顺手加了日志系统、加了权限框架。

错在哪：范围蔓延的直接来源。不做清单是给 S6 审查方看的——审查方据此判断「多出来的东西」是否越界。

**反例 5：依赖图有环**
> T-03 前置 T-04，T-04 前置 T-03。

错在哪：说明切分线切错了（两个任务其实是同一件事的两半）。必须合并或重新切。

## 六、与上下游的衔接

**允许进入 S3 的条件（全满足）**
1. 任务表每行四要素非空，验收点全部可观察。
2. 依赖图连通、无环、无孤立任务。
3. 每条 `AC-xx` 至少映射到一个任务；每个任务至少服务一条 `AC-xx`（否则删掉这个任务）。
4. 有「本期不做」≥3 条。
5. 闸二 rc=0。

**必须退回的情况**
- 拆不出可独立验证的任务 → 退回 S1，说明现状边界没摸清。
- 验收点无法映射回 PRD 的 AC → 退回 S1 补需求映射（很可能 AC 本身不可测，属 PRD 缺陷）。
- 探针任务失败（技术上做不到）→ 退回 S1 冲突清单，⛔ 不许在 S3 边做边改需求。

## 七、自检清单

- [ ] 任务编号连续无跳号，前置编号都真实存在
- [ ] 每个任务的影响文件 ≤ 5
- [ ] 每条验收点都能复制粘贴直接跑
- [ ] 每个任务的回滚动作确定、可执行、不需要「想一下」
- [ ] 数据迁移类任务标了「可逆 / 不可逆」
- [ ] 「本期不做」≥3 条且各有理由
- [ ] 无「预计工时」类不可核估算（工期若必须给，单列且标「估算，不作判据」）
