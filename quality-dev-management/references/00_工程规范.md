# 工程规范（本 Skill 内置 · 判据唯一源）

> 本文件是 `quality-dev-management` **自带的**工程质量规范，包内自包含，不依赖任何外部文档。
> `SKILL.md` 里出现的每条判据，出处都在这里；两者冲突时**以本文件为准**，并顺手把 `SKILL.md` 改一致。
> 为什么单独立一份：判据散落在八个 reference 里会漂移，收在一处才改得动。

---

## 一、执行五步（接到任何指令，一律照做，不许跳步）

> 原话：「调查事实、摸清底数、对标成熟方案、先出方案、最后执行。想清楚不做什么，比想做什么更重要。」

| 步 | 动作 | 硬要求 | 判据 |
|---|---|---|---|
| **1 调查事实** | 先查现状，不凭印象下手 | ⛔ 禁「来了就做」；⛔ 禁先定方案后找依据 | 给出**实测数字 / 路径** |
| **2 摸清底数** | 盘既有机制与存量 | 先查既有件，⛔ 禁重复造轮子 | 「已有什么 / 缺什么 / 存量多少」量化 |
| **3 对标成熟方案** | 先看业界怎么做 | ⛔ 禁拍脑袋自创 | 对标结论 + **映射到自己这边** |
| **4 先出方案** | 出方案不执行 | 附**依据四问**；不可逆项单列待裁 | 获认可后才动手 |
| **5 最后执行** | 按序做 + 自测 + 反向变异 | 判据必反向验证「真抓」而非崩溃假抓 | 自测全绿 + 变异全中 |

**配套四问之上再加一问：这次我拒绝做什么？**
多数事故不是做错了什么，而是**做了不该做的**。

**跳步的代价是可测的**：造重复件、写了规范却没落地、假陈述——三者都源于跳过 1~4 直接执行。

## 二、依据四问（凡提交方案必附）

⛔ 只给「结论 / 建议 X」而不给依据 ⇒ 不算完成。缺项必须显式写「此项无」+ 为什么无。

| # | 问什么 | 写法要求 | ⛔ 反面写法 |
|---|---|---|---|
| 1 | 这是一个什么问题？ | 给**归类名 + 一句话定性** | 直接从结论开头 |
| 2 | 产生原因是什么？ | 讲**机制**（为什么会走到这一步） | 罗列时间线、复述经过、甩锅 |
| 3 | 有哪些影响？ | 后果落在谁身上、是「堵住」还是「放错」，**含不做的代价** | 只写「有风险」；只说好处不说代价 |
| 4 | 推荐怎么做？ | **明确倾向 + 理由**，理由挂到第 2 或第 3 条 | 「都行」「看情况」「你定」 |

**第 4 问不许和稀泥**：允许多方案并列（甲 / 乙），但必须标出推荐哪个 + 为什么；
确属只能对方裁的（涉商业资产、删数据），写明「依据到此为止，属你裁量」，并说清**不裁的后果**。

**不触发的情形**：纯事实汇报、纯问答、纯命令执行回执（须写明「本条为执行回执，非方案」）。

## 三、rc 四档（所有闸 / 校验 / 自查脚本的唯一退出码口径）

| rc | 语义 | 一句话判定（能回答「谁错了」） |
|---|---|---|
| 0 | 干净 / 全过 | 判据跑完了，结论「没问题」 |
| 1 | **检出** | 判据跑完了，确实有东西该拦（业务问题，归施工方改） |
| 2 | **调用层崩了** | 脚本自己坏：Traceback / 未捕获异常 / 内部不一致 |
| 3 | **判据不可用（报灰）** | 闸给不出可信结论：输入缺失损坏、环境缺依赖、配置不可读、**用法错** |

**三条硬纪律**：

1. 判据不可用 ⛔ 绝不返回 0 ——「没查出来」≠「没问题」。
2. 业务检出必须落 1，⛔ 不写成 2。
3. rc ∈ {2, 3} = **「没结论」**：调用方 ⛔ 既不当通过也不当检出，只能报灰重试或人工介入。

**★ 用法错归 3**：argparse 默认 `exit(2)` **必须覆写为 3** —— 命令写错既不是「检出」也不是「崩了」，是这次运行给不出有效结论。

**★ docstring 自称有灰档的脚本，实现里必须有真 rc=3 分支**（`rc=3` / `RC_UNAVAILABLE` / `exit(3)`）。声称有而没写 = 空头承诺，比没有更糟。

> 为什么如此在意 2 和 3 的分界：把「环境缺依赖」报成「检出」，施工方会去改业务代码，改一圈发现白改；把「检出」报成「崩了」，调用方会重试，重试一百次也还是红的。

## 四、反向变异必带对照组

**问题**：反向变异红了，不代表判据抓到了东西 —— 也可能是环境坏了、依赖没定位、脚本自己崩了。

**做法**：同环境、同数据跑两遍 —— 改坏的那遍**必须红**，不改的那遍**必须绿**。

| 记录列 | 内容 |
|---|---|
| 变异点 | 改了哪一行 / 哪个判据 |
| 期望红 | 期望以什么形态红（rc=1？某条断言？） |
| 实测 rc | 实际跑出来的 rc |
| **对照组 rc** | 不改坏的那遍跑出来的 rc，**必须是 0** |

缺对照组 = 无法区分「真抓」与「假红」，判据形同未验。

**先确认依赖可定位再跑**：判据本身有毛病时先修判据，别拿一个坏判据去测另一个坏判据。

**断言不许依赖机器实时状态**：写「能抢到锁」这种断言，机器一忙就红 → 变成看运气。做法：桩掉依赖，**两种分支都断言**（抢到 + 被拦），再补一条反向验证（桩一个失败场景，确认真的会拦住 / 真的会放行）。

## 五、验证「调用」而不是「定义」

判定一项能力是否真的生效，三级递增，**只有最后一级才算数**：

| 级别 | 证据 | 能证明什么 |
|---|---|---|
| 1 | `grep` 到函数名 / 字段名 | 只证明**写了** |
| 2 | 读入口函数体，有调用形态（`inspect.getsource(main)`） | 证明**接了** |
| 3 | 喂违规输入拿到 `rc=1`（或等价行为证据） | 证明**拦得住** ← 只有这级算数 |

⛔ 函数存在、docstring 漂亮、grep 命中 —— 全都可以**永不执行**。

**放宽 / 收紧类判据必须双向**：阈值、豁免、白名单类判据，两个方向各一 case ——
一个证「该红的红了」，一个证「不该红的没红」。⛔ 只测一边，交付方一放宽断言照绿、真漏检却一条没修。

## 六、审查方 ≠ 施工方

**独立审查必须换身份、只读**：不写一个字节的源码，只出报告。

| 不算独立审查 | 原因 |
|---|---|
| 自审 | 同一个人看不到自己的盲区 |
| 同一角色再审一遍 | 判据没换，结论不会变 |
| 施工方中途参与的「复审」 | 立场未变 |
| 拿「验收」当「已过审」 | 验收核的是「做没做」，审查核的是「做得对不对」 |

⇒ **`已完成` = 独立审查通过 ＋ 验收通过，缺一不可。**

**代码审查会话铁律**：只读（改任何源码 / 配置都禁止，报告本身除外）；
流程 ① 先读需求文档 ② 再读全部源码 ③ 按三级输出 ④ 每条含真实 `文件路径:行号` + 代码片段 + 触发条件与后果 + 可落地修法 ⑤ 末尾给修复优先级。
**⛔ 严禁编造行号或代码。**

### 审查三级判据

| 级别 | 判据 | 例 |
|---|---|---|
| 🔴 **Blocker** | 会导致数据损坏 / 安全漏洞 / 功能完全不可用 / 判据失效（该拦的拦不住） | 路径拼接未校验导致任意写；闸门恒真断言（`assert True`） |
| 🟡 **Suggestion** | 不修也能用，但在特定条件下会出错或明显劣化 | 异常分支只 `except: pass`；边界值未处理 |
| 💭 **Nit** | 风格 / 命名 / 注释，不影响行为 | 变量名拼写；注释与代码不符 |

每条必须含四要素，缺一不算合格条目：

```
<file>:<line>          ← 真实路径与行号，回读能对上
<代码片段>              ← 贴原文，不转述
<触发条件与后果>        ← 什么输入 / 什么状态下会出事，出什么事
<可落地修法>            ← 能直接照做，不是「建议优化」
```

⛔ 不许写「可能存在 SQL 注入」这种无编号无位置的结论。
⛔ 不许用「建议优化一下」这种不可落地的措辞。

## 七、闸门分层与置信度降级

**四层闸门，越往后越不可关**：

| 层 | 位置 | 能否本地关 | 职责 |
|---|---|---|---|
| 1 | pre-commit | **可关** | 只拦高置信，快 |
| 2 | pre-receive | ⛔ 不可关 | 拦绕过本地检查的提交 |
| 3 | CI required | ⛔ 不可关 | 全量跑，合并前必过 |
| 4 | 制品扫描 | ⛔ 不可关 | 发布前最后一道 |

**档位：`block → warn → ⛔ 禁止 silent-off`**

| 置信度 | 档位 | 要求 |
|---|---|---|
| high | **block** | 直接拦 |
| mid / low | **warn** | **必须留痕 + 有责任人 + 可升级** |
| — | silent-off | ⛔ **绝对禁止**。关闸必告警 |

**为什么置信度要和档位挂钩**：把中低置信判据做成 block，会消耗信任并诱导开发者绕过整道闸 —— 最后连高置信判据也一起失效。**宁降 warn，不硬 block。**

## 八、自测可靠性的几条硬要求

以下是**最常踩的几条**（不是完整清单，遇到新坑就往下加）：

1. **不用正常数据测异常分支**。正常数据永远走不到兜底分支。
   做法：先用探针打印候选字段的非空计数，**取计数为 0 的那个当样本**。
   ⚠ 同一概念常有一空一满两个字段，看错就看不出问题。
2. **低频路径用打桩强制走**。把依赖全桩掉，只验参数流转与回调形态 —— 比等一个真样样快且稳定。
3. **打桩要打到「真实入口」**，别直接调内部函数 —— 否则绕过的东西测不到。
4. **数 Python 函数实参用 `ast`，不能数逗号**。`on_progress(min(0.99, x/total))` 的逗号在 `min()` 里面，实际只传 1 个参数。
   做法：`ast.parse` + `len(node.args) + len(node.keywords)`。
5. **源码子串断言先剥 `#` 注释**。要找的字样只在注释里 ⇒ 一路绿灯但功能没接（假绿）；
   注释里解释规则的话撞红断言 ⇒ 误伤。
   ⚠ 改注释绕开**不是修，是把闸门拆了**。做法：用 `tokenize` 只删 `COMMENT`、行数不变、保留字符串与 docstring。
6. **`except: pass` 必须改留痕**。它会把真凶吞掉 —— 现象是「输出全空」，查半天发现异常被吃了。
7. **完整性不能只看存在与大小**。要验真实内容（文件头、可解析性、非零实际尺寸）。
8. **自测条数是恒定量**。换台机器缺依赖只该动「跳过」数，不该动「总数」—— 总数变了说明有断言被静默跳过。
9. **错误不许静默**。入口对**错类型**必须判、必须报警，⛔ 不许静默回落默认值。
   典型现场：传进来 `None`，代码 `value = arg or default` 直接吞掉 —— 上层以为配置生效了，实际用的是默认值，行为对不上排查半天。
10. **临时切全局态必须成对切回**。环境变量、时区、locale、mock、工作目录 —— 改了就在 `finally` 里切回，并在节末自证「已复原」。
    不回切会让同一进程里后面的用例莫名变红，且红的位置和真凶完全无关。

## 九、产物核查与返工

- **只重做有问题的部分**：整篇重写会引入未被审查覆盖的新代码。
- **改前先打指纹**（commit 或 `sha256` 清单），否则改完无法证明「只改了该改的」。
- **续跑先比指纹**：指纹变了说明有人在中间动过，停手问人，别硬改。
- **rc=3 是没结论**，不是通过也不是检出。必须先修清单或环境再跑。
