# S1 项目评估

> 位置：整条链的第一环。上游是 `pm-prd-generator` 交付的 `PRD_v<x>.md`（只读），下游是 S2 施工计划。
> 本阶段唯一不可替代的价值：**在动手之前把 PRD 与现状的冲突摆到桌面上**。⛔ 不许照单全收。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 摸清现状 | 现状基线有实测数字：文件数 / 行数 / 已有能力清单 / 现有测试 rc |
| 把 PRD 映射到现状 | 每条 R/F 编号都有落点：`现成可用` / `要改` / `新建` / `做不到` |
| **指出冲突** | 冲突清单每条含 `PRD 行号 + 现状 file:line + 冲突描述 + 建议 + 归属` |
| 给可行性结论 | 结论落到「能按 PRD 做 / 要做取舍 / 需要改 PRD」三档之一，并说明理由 |
| 走完五步前两步 | 报告里有「调查事实」「摸清底数」两节，各带实测数据 |

本阶段的闸门：`acceptance_gate.py` 检查评估报告存在、含「冲突清单」与「现状基线」两节、每条冲突行数 ≥ 3 列可解析。rc=0 才进 S2。

## 二、输入（缺一样就不许开工）

1. `PRD_v<x>.md` 的绝对路径，且能被读（⛔ 不接受「PRD 在我脑子里」）。
2. 代码库根目录路径（新建项目则为空目录 + 目标技术栈）。
3. 运行环境事实：语言版本、包管理器、能否联网、有无现成测试框架。
4. 冲突裁决人是谁（谁能拍板「改 PRD」还是「改实现」）。

**前置检查**：先跑一次现状基线（`git log -1`、目录文件数、现有测试命令的 rc）。跑不出来就说明环境有问题，先解决环境，⛔ 不许拿「大概能跑」当基线。

## 三、操作步骤

**A1 调查事实（五步走第 1 步）**
1. 读 PRD 全文，抽出全部 `R-xx` / `F-xx` / `AC-xx` 编号，列成清单。
2. 读现状：目录结构、入口文件、数据层、配置、测试目录。⛔ 不许只看 README 就断言现状。
3. 跑一次现状基线并记 rc：现有测试、构建命令、lint。跑不动就记「不可运行 + 原因」。
4. 所有数字标出处：`路径` 或 `命令 + rc`。⛔ 不写「约几千行」这种估算。

**A2 摸清底数（五步走第 2 步）**
回答三问并量化：已有什么（可复用模块 / 已有表 / 已有接口）、缺什么（要新建的清单）、存量多少（文件数、行数、测试覆盖哪些）。

**A3 逐条映射**
每条 PRD 要求填一格：`现成可用`（已有实现，指路径）/ `要改`（改哪个文件哪段）/ `新建`（新文件清单）/ `做不到`（为什么，卡在哪）。

**A4 找冲突（本阶段的核心动作）**
逐条问四个问题，任一为「是」就进冲突清单：
- PRD 要求的行为与现有实现相反？（例：PRD 要求软删除，现状是物理删除）
- PRD 依赖的能力现状没有且短期做不出来？（例：要求实时推送，现状无长连接基础设施）
- PRD 的验收标准与现有数据结构不兼容？（例：要求按用户维度统计，现表无 user_id）
- PRD 内部自相矛盾或与已知约束打架？（例：AC 要求毫秒级响应，同时要求全量加密落盘）

每条冲突必须写**归属**：`改 PRD`（实现侧说服产品改）/ `改实现`（实现侧认账）/ `待裁决`（必须由人拍）。⛔ 不许全部塞进「待裁决」当免责。

**A5 给路径（五步走第 4 步）**
给 ≥3 条路径（不止二选一），每条写代价、风险、我推荐哪条及理由。理由要挂到 A1/A2 的实测数据上。

每条要给人的建议（含冲突建议）按`00_工程规范.md` §二 附**依据四问**，顺序固定：

| # | 问什么 | 反面写法 |
|---|---|---|
| 1 | 这是一个什么问题？（归类名 + 一句话定性） | 直接从结论开头 |
| 2 | 产生原因是什么？（讲机制，不讲情绪、不复述经过） | 罗列时间线 / 甩锅 |
| 3 | 有哪些影响？（落在谁身上、堵住还是放错、不做的代价） | 只写「有风险」 |
| 4 | 推荐怎么做？（明确倾向 + 理由要挂回第 2/3 条） | 「都行」「看情况」「决策者定」 |

⛔ 第 4 问不许和稀泥：可以甲乙并列，但必须标推荐哪个、为什么。确需人裁的（涉数据删除、商业资产）写明「依据到此为止，属裁量项」并说清不裁的后果。

**A6 收口**
跑闸 → 出评估报告 → 交冲突裁决 → 拿到裁决结论才进 S2。

## 四、输出模板

### 4.1 评估报告骨架

```markdown
# 项目评估报告 · <项目名> · <日期>

## 1 输入事实
- PRD：<绝对路径> · 版本 v<x> · 需求条数 R=<n> / F=<n> / AC=<n>
- 代码库：<绝对路径> · 文件数=<n> · 源码行数=<n>（命令：<cmd>）
- 环境：<语言版本> · <包管理器> · 联网=<是/否> · 测试框架=<有/无>

## 2 现状基线（调查事实）
| 项 | 实测值 | 出处 |
|---|---|---|
| 现有测试 | rc=<0/1/2/3> | `<cmd>` |
| 构建 | rc=<n> | `<cmd>` |
| 入口文件 | `<path>:<line>` | 读文件 |

## 3 底数（已有什么 / 缺什么 / 存量多少）
- 已有什么：<模块 → 路径 → 可复用程度>
- 缺什么：<能力 → 需新建文件>
- 存量：<n> 文件 / <n> 行 / 测试覆盖 <范围>

## 4 需求映射
| 编号 | 要求摘要 | 落点类型 | 落点 | 影响面 |
|---|---|---|---|---|
| R-01 | … | 现成可用 | `src/a.py:12` | 无 |
| F-03 | … | 要改 | `src/b.py:40-88` | 中 |
| F-07 | … | 新建 | `src/c.py` | 高 |
| F-09 | … | 做不到 | 无长连接设施 | 阻塞 |

## 5 冲突清单（本阶段的核心产出）
| # | PRD 位置 | 现状证据 | 冲突描述 | 建议 | 归属 |
|---|---|---|---|---|---|
| C-01 | `PRD_v1.0.md:88` | `src/db.py:31` 物理删除 | PRD 要求软删除，现状删了就没了 | 加 `deleted_at`，迁移脚本回填 | 改实现 |
| C-02 | `PRD_v1.0.md:132` | 表无 `user_id` | AC 要按用户统计，现表缺维度 | 改 PRD：本期按租户统计 | 待裁决 |

## 6 路径与推荐
- 路径甲：… 代价 … 风险 …
- 路径乙：… 代价 … 风险 …
- 路径丙：… 代价 … 风险 …
- 推荐：<哪条>，理由挂 §2/§3 的哪个数字。

## 7 结论
<能按 PRD 做 / 要做取舍（列取舍项）/ 需要改 PRD（列改哪几条）>
```

### 4.2 冲突清单的四列硬要求

`PRD 位置` 必须能回读（行号或章节号）；`现状证据` 必须是 `file:line` 或命令 rc；`建议` 必须是一条能执行的动作；`归属` 只能三选一。

## 五、反例

**反例 1：把 PRD 当圣旨，一条冲突都不提**
> 报告写「PRD 明确，现状可支撑，评估通过」，冲突清单空。

错在哪：PRD 是产品视角写的，不可能知道现有表结构、现有事务边界、现有性能天花板。零冲突 = 没读现状，只读了 PRD。判据上表现为「冲突清单 0 行」，闸一应当拦下。

**反例 2：冲突写成「可能有风险」**
> 「C-01：软删除改造可能影响查询性能，建议关注。」

错在哪：没有 `PRD 行号`、没有 `file:line`、没有可执行动作、没有归属。「建议关注」是不可核措辞，S7 无法据此整改，审查方无法据此验证。

**反例 3：把「做不到」写成「有挑战」**
> 「实时推送有一定挑战，建议后续优化。」

错在哪：回避了阻塞结论，把 S1 的判断责任推给 S2/S3。结果是 S3 做到一半发现做不了，回头改 PRD，前面全白干。做不到就必须写「做不到 + 卡点 + 归属=改 PRD」。

**反例 4：一次评估就想定排期**
> 报告里出现「预计 3 天完成 F-03」。

错在哪：本阶段只管「能不能做、有没有冲突」，工期是 S2 拆完任务才有的东西；此处给的数字没有任务粒度支撑，属编造。

## 六、与上下游的衔接

**允许进入 S2 的条件（全满足）**
1. 评估报告七节齐全，§2 与 §3 的数字都有出处。
2. 冲突清单每条四列齐，且 `归属` 不为空。
3. 所有 `待裁决` 项已拿到人的裁决结论（写进报告 §7）。
4. 闸一 rc=0。

**必须退回的情况**
- 发现 PRD 关键条款缺失/自相矛盾 → 退回 `pm-prd-generator` 补 PRD，⛔ 不许自己补需求。
- 现状基线跑不起来（环境坏）→ 停在 S1，先修环境；⛔ 不许带病进 S2。
- 冲突全被判「改 PRD」→ 回到产品侧改 PRD 后**重跑 S1**，⛔ 不许拿旧评估继续。

## 七、自检清单（逐条打勾，不过就补）

- [ ] 每条 PRD 编号都有映射行，无遗漏（数量对得上）
- [ ] 现状数字全部有 `路径` 或 `命令 + rc`
- [ ] 冲突清单非空（真空也要写「逐条比对后 0 冲突」+ 比对方法）
- [ ] 每条冲突能回读到 PRD 的具体行
- [ ] 每条冲突的现状证据能点到 `file:line`
- [ ] 每条冲突有归属，无「待裁决」残留
- [ ] 给了 ≥3 条路径，且标了推荐与理由
- [ ] 报告里没有「预计工期」「大概」这类不可核表述
