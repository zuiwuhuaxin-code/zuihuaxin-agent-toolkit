# S6 独立审查

> 位置：蓝队防守之后，闭环完善之前。
> 本阶段唯一不可替代的价值：**换一个人、只读、先读 PRD，从外部判断「这堆代码到底能不能验收」**。
> ⛔ 自审不算独立审查（`00_工程规范.md` §六）；施工方中途参与的「复审」也不算。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 换身份 | 报告开头写明审查身份与施工身份不同，且 `git status --porcelain` 为空（零改动） |
| 先读 PRD | 报告第一章是「依据 PRD 的验收标准」，每条挂 `PRD 行号` |
| 验收标准可观察 | 每条标准是 rc / 文件 / 行数 / 字段值，⛔ 无「功能正常」 |
| 测试用例可执行 | 每条用例给输入、步骤、期望、对应验收标准编号 |
| 三级输出 | 条目分 🔴Blocker / 🟡Suggestion / 💭Nit，每条含 `file:line + 代码片段 + 触发条件与后果 + 落地修法` |
| 无编造 | 每条 `file:line` 回读能对上；⛔ 严禁编造行号或代码 |
| 有结论 | 末尾给「能否验收」+ 修复优先级 |

闸（进 S7 前）：`acceptance_gate.py` 检查审查报告含「验收标准」「测试用例」「Blocker」三节，且 `:行号` 形式的引用数 ≥ 条目数。rc=0 才进 S7。

## 二、输入

1. `PRD_v<x>.md`（**必须第一份读**，⛔ 不许先读代码再回头找需求）。
2. 全部源码（S7 之前的版本）。
3. 红队报告 + 蓝队防御报告（作为交叉证据，⛔ 不替代自己读代码）。
4. S3 自测记录（看施工方声称的覆盖，⛔ 不采信其结论，只采信证据）。

**前置检查**：确认自己没有写权（或承诺不用写权）。审查期间任何源码/配置改动都会让「只读」失效，报告作废重来。

## 三、铁律（引自 `00_工程规范.md` §六，逐条照做）

原文（`00_工程规范.md` §六）：

> **代码审查会话铁律**：只读（改任何 `.py`/`.json` 都禁止，报告本身除外）；流程 ① 先读需求文档
> ② 再读全部源码 ③ 按 🔴Blocker / 🟡Suggestion / 💭Nit 三级输出 ④ 每条含**真实 文件路径:行号 +
> 代码片段 + 触发条件与后果 + 可落地修法** ⑤ 末尾给修复优先级。**严禁编造行号或代码**。

拆成五条硬要求：

1. **只读**：除报告本身，一个字节都不写。证据 = 审查前后 `git status --porcelain` 均为空。
2. **先读需求文档再读源码**：顺序不可颠倒。先读代码会让人按实现去解释需求，把「实现没做到」看成「需求就是这样」。
3. **三级分类**：🔴Blocker（必须改，不改不能验收）/ 🟡Suggestion（该改，可排期）/ 💭Nit（风格，可忽略）。
4. **每条四要素**：真实 `路径:行号` + 代码片段 + 触发条件与后果 + 可落地修法。
5. **末尾修复优先级**：谁先改、改完怎么验。

⛔ 补充边界（`00_工程规范.md` §六）：`已完成` = 独立审查通过 **且** 验收通过，缺一不可；拿「验收通过」当「已过审」是整类漏判。

## 四、操作步骤

**F1 明确身份与边界**
报告开头写：审查方身份 / 施工方身份 / 审查范围 / 审查日期 / 承诺只读。身份必须真的不同（不同会话或不同角色设定）。

**F2 先读 PRD，抽验收标准**
逐条抽 `R/F/AC`，转成可观察标准。PRD 的 AC 不可观察时，**自己写可观察版本并标注「我方细化，需 PRD 确认」**，⛔ 不许默默替换标准。

**F3 写测试用例（先于读代码）**
基于验收标准写用例：输入、步骤、期望。此时不看实现，避免被实现带偏。用例要覆盖正例 / 反例 / 边界。

**F4 读全部源码**
按模块顺序读，边读边记候选问题。⛔ 不许抽样读——「全部源码」是铁律第 ② 条。读的时候记真实行号，读完立刻回读核对。

**F5 分类与成文**
候选按三级分类；每条补四要素。分类判据：
- 🔴 会导致数据错/丢、安全缺口、验收标准不满足、崩溃 → Blocker。
- 🟡 会导致将来出错、可维护性显著受损、错误处理缺失但不致命 → Suggestion。
- 💭 命名、格式、注释 → Nit。

**F6 交叉核对红蓝报告**
红队的 `E-xx`、蓝队的机制，逐条问「我在代码里看到了吗」。⛔ 不采信报告结论，只采信代码事实。报告说修了但代码里没有 = Blocker（虚假陈述比缺口更严重）。

**F7 给结论与优先级**
「能否验收」二选一 + 理由；修复优先级列表（Blocker 全列，Suggestion 排前 5）。

**F8 自证只读**
跑 `git status --porcelain`，输出为空 → 写进报告附录。

## 五、输出模板

### 5.1 报告骨架

```markdown
# 独立审查报告 · <项目名> · <日期>

## 0 审查身份与边界
- 审查方：<身份>（与施工方 <身份> 不同）
- 审查范围：<路径/模块清单>，共 <n> 文件 / <n> 行
- 只读自证：审查前 `git status --porcelain` 为空；审查后为空（见附录 A）
- 依据：PRD `<路径>` v<x>；红队报告；蓝队报告

## 1 验收标准（依据 PRD，先于读代码写）
| 编号 | PRD 位置 | 验收标准（可观察） | 来源 |
|---|---|---|---|
| VA-01 | `PRD_v1.0.md:44` | 提交空表单 → 返回 400，且无记录写入（表行数不变） | AC-01 原样 |
| VA-02 | `PRD_v1.0.md:61` | 导出他人数据 → 403 | AC-03 我方细化（PRD 写「不能越权」） |

## 2 测试用例
| 编号 | 对应 VA | 类型 | 输入 / 步骤 | 期望 | 实测 | 结论 |
|---|---|---|---|---|---|---|
| TC-01 | VA-01 | 反例 | POST 空 body | 400 + 行数不变 | 400，行数不变 | 过 |
| TC-02 | VA-02 | 反例 | 改 id 导出 | 403 | **200，返回他人数据** | **不过** |

## 3 审查条目
### 3.1 🔴 Blocker
#### B-01 导出接口缺归属校验（对应 E-02 / TC-02）
- 位置：`src/export.py:61`
- 代码片段：
  ```python
  rows = db.query("select * from records where id = ?", (req.args["id"],))
  ```
- 触发条件与后果：任何登录用户把 `id` 改成他人记录 id，即可导出他人全量数据；水平越权，数据泄露不可逆。
- 落地修法：查询前加 `owner_id = current_user.id` 条件，命中 0 行返回 404（不返回 403，避免探测存在性）。

### 3.2 🟡 Suggestion
#### S-01 上传白名单未拒绝双扩展名
- 位置：`src/upload.py:34` …（四要素同上）

### 3.3 💭 Nit
#### N-01 `src/db.py:12` 变量名 `d` 语义不明
- 位置 / 片段 / 影响（仅可读性）/ 修法（改名 `conn`）

## 4 与红蓝报告的对账
| 来源 | 声称 | 代码事实 | 判定 |
|---|---|---|---|
| 蓝队 §3.1 | E-02 已修 | `src/export.py:61` 仍无归属判定 | **虚假陈述，Blocker** |

## 5 结论
- 能否验收：**否**
- 理由：B-01 直接违反 VA-02；另有 <n> 条 Blocker。
- 修复优先级：B-01 → B-02 → … → S-01~S-05

## 附录 A 只读自证
`git status --porcelain` 输出：（空）
```

### 5.2 每条条目的四要素检查

| 要素 | 不合格形态 | 合格形态 |
|---|---|---|
| 位置 | 「在导出模块里」 | `src/export.py:61` |
| 代码片段 | 转述「查询没带 owner」 | 原样贴那 1~3 行 |
| 触发条件与后果 | 「有越权风险」 | 「登录用户改 id 即可读他人数据；泄露不可逆」 |
| 修法 | 「加权限校验」 | 「查询加 `owner_id` 条件，0 行返回 404」 |

## 六、反例

**反例 1：施工方自己出审查报告**
> 报告署名与施工方同一身份，结论「已自查，无 Blocker」。

错在哪：直接违反 H3 / `00_工程规范.md` §六。自审的系统性偏差是「按自己写代码时的假设去验证」，恰好漏掉自己没想到的分支。此报告无效，须换身份重审。

**反例 2：先读代码后补验收标准**
> 报告里验收标准的措辞与实现细节高度一致，明显是照着实现反推的。

错在哪：违反铁律第 ① ② 条顺序。这样写出来的标准一定「恰好」满足，等于没有标准。判据：验收标准里若出现实现内部细节（函数名、表名），高度可疑。

**反例 3：编造行号**
> 条目写 `src/api.py:187`，但该文件只有 120 行。

错在哪：铁律明令「严禁编造行号或代码」。行号是审查方唯一可被复核的东西，编造一次整份报告的可信度归零。**每条行号必须回读确认。**

**反例 4：全是 Nit，没有 Blocker**
> 30 条条目全在讲命名与缩进，结论「可以验收」。

错在哪：S4/S5 已经找出过 `E` 级缺口，审查方一条 Blocker 都没发现，说明没读代码或没读 PRD。判据：报告若 0 Blocker 而红队报告有 block 级 E，必须解释差异。

**反例 5：只说「建议优化」**
> 「建议优化导出接口的权限处理。」

错在哪：不可落地。S7 拿这条无法整改，S6 复核时也无法判定是否改到位。修法必须是可执行动作。

**反例 6：审查中顺手修了 bug**
> 「发现一个空指针，我直接改了。」

错在哪：破坏只读边界，审查报告与代码版本不再对应，后续 `file:line` 全部失真。发现即记录，⛔ 不动手。

## 七、与上下游的衔接

**允许进入 S7 的条件（全满足）**
1. 报告七节齐全（身份/验收标准/用例/条目/对账/结论/只读自证）。
2. 每条条目四要素齐，行号回读能对上。
3. 验收标准全部可观察，且能追到 PRD。
4. 结论明确（能/不能验收），Blocker 全列。
5. 只读自证为空输出。
6. 闸 rc=0。

**必须退回的情况**
- 发现 PRD 本身不可验收（AC 不可观察且无法细化）→ 退回 `pm-prd-generator`，⛔ 不许自己定标准然后自己验收。
- 审查身份与施工身份相同 → 重审，⛔ 不许「补个签名」了事。
- 代码在审查期间被改过（`git status` 非空）→ 报告作废，回到审查起点。

## 八、自检清单

- [ ] 审查身份 ≠ 施工身份，写在报告开头
- [ ] 验收标准章节在测试用例之前、在源码阅读之前
- [ ] 每条验收标准可观察且挂 PRD 位置
- [ ] 测试用例覆盖正例/反例/边界，每条挂 VA 编号
- [ ] 条目分三级，每条四要素齐
- [ ] 所有行号回读核对过（抽 100% 或至少每条都点开看过）
- [ ] 与红蓝报告做过对账，虚假陈述单列
- [ ] 结论二选一明确，附修复优先级
- [ ] `git status --porcelain` 为空并写入附录
- [ ] 报告里没有「可能 / 建议关注 / 优化一下」这类不可落地措辞
