# S3 编码与自测

> 位置：施工计划之后，红队攻防之前。
> 本阶段唯一不可替代的价值：**证「代码在按判据工作」，而不是「代码跑起来了」**。核心手段是反向变异 + 对照组。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 按计划顺序落地 | 每个任务有对应提交/变更集，提交信息含任务编号 |
| 自测三面齐 | 正例 / 反例 / 边界各有用例，且全部实际执行 |
| 自测真能抓错 | 反向变异记录里每条都有「变异点 / 期望红 / 实测 rc / 对照组 rc」四列 |
| 语法与静态门过 | `python -m py_compile`（或其他语言等价）rc=0 |
| 判据未被放水 | 变异后判据仍能红；若为变绿而改过判据，须有审计行 |

闸三（进 S4 前）：`acceptance_gate.py` 检查自测记录含「反向变异」节且对照组列非空，测试命令 rc=0。

## 二、输入

1. S2 施工计划（任务表 + 验收点）。
2. S1 冲突裁决结论（哪些按 PRD、哪些按现状）。
3. 现有测试框架与跑法（没有就先建最小可跑框架，⛔ 不许「这次先不写测试」）。

## 三、编码纪律（五条，违反即返工）

1. **一次只做一件事**：一个任务一个变更集，⛔ 不顺手重构（顺手改会把 S6 审查范围炸开）。
2. **先写判据再写实现**：能先写失败用例就先写，看它红，再让它绿。⛔ 不许先写完再补测试来凑绿。
3. **错误不许静默**：入口对错类型必须判、必须报警，⛔ 不许静默回落默认值（依据：`00_工程规范.md` §八 第 9 条）。
4. **临时切全局态必须成对切回**（环境变量、时区、locale、mock），节末自证（依据：`00_工程规范.md` §八 第 10 条）。
5. **写盘纯 LF**：文本产物用 `Path.write_text(s, encoding="utf-8", newline="\n")` 或 `write_bytes`。

## 四、自测三面（缺一面不算自测）

### 4.1 正例
覆盖「这条代码为什么存在」的那个场景。⛔ 最常见的错是：用例走的是不该由这段代码负责的分支（依据：`00_工程规范.md` §八「用例别只走好走的那条路」）。

**判据**：每个公开函数/接口至少一条正例；正例的输入必须真的落在该函数负责的分支上（可在用例里打印分支标记自证）。

### 4.2 反例
该被拦住的输入必须被拦住：非法参数、越权访问、类型错、缺字段。

**挑数据的判据**：⛔ 不用正常数据测异常分支——正常数据永远走不到兜底分支（依据：`00_工程规范.md` §八 第 1 条）。做法：先用探针打印候选字段的非空计数，取计数为 0 的那个当样本。

**判据**：反例断言的是「返回错误码 / 抛出指定异常 / 拒绝写入」，⛔ 不是「没崩」。「没崩」是弱断言。

### 4.3 边界
至少覆盖：空值 / 0 / 负数 / 超长 / 单元素 / 上限+1 / 重复调用（幂等）/ 并发或重入。

**判据**：边界用例要断言具体行为（截断到多少字符、返回哪个错误码），不是「能跑完」。

## 五、反向变异（本阶段的重头戏）

### 5.1 为什么要做
自测全绿只证明「断言没红」，不证明「断言有用」。变异测试是唯一能证「判据真的会抓坏代码」的手段（依据：`00_工程规范.md` §五「自测全绿不等于判据有效 ⇒ 必须反向攻它」）。

### 5.2 与对照组的关系（`00_工程规范.md` §四）
反向变异的另一侧是**假红**：把代码改坏后测试红了，但红的原因可能是依赖没定位、网络抖、路径错、脚本自己崩了。**缺对照组就无法区分「真抓」与「假红」**。

**标准跑法（同环境、同数据、连续两次）**：
1. 跑对照组：代码不变 → 期望 rc=0（绿）。不绿就先修环境，⛔ 不许继续。
2. 施加变异（只改一处）→ 期望 rc=1（红），且**红的断言必须就是覆盖该处的断言**。
3. 撤销变异（`git checkout -- <file>` 或还原补丁）→ 再跑一次 → 期望 rc=0，证明变异已完全撤销。

三步构成一组，四列记录。⛔ 只跑第 2 步 = 半边测。

### 5.3 变异清单（每类至少一条）

| 变异类型 | 怎么改 | 期望怎么红 | 对照组怎么绿 |
|---|---|---|---|
| 判据反转 | `if x > 0` → `if x >= 0`（或删掉整条校验） | 边界用例 `x=0` 由拒绝变通过 → 断言失败 | 不改时 `x=0` 被拒 → 用例绿 |
| 返回值篡改 | `return 401` → `return 200` | 反例断言「应 401」失败 | 不改时返回 401 |
| 静默吞错 | 删掉 `raise`，改成 `pass` | 反例断言「应抛异常」失败 | 不改时抛出 |
| 早返回短路 | 函数首行加 `return None` | 正例断言「应返回对象」失败 | 不改时返回对象 |
| 常量偏移 | 上限 `100` → `101` | 边界用例 `100/101` 断言失败 | 不改时 101 被拒 |
| 顺序调换 | 两条校验互换（先查权限后查登录） | 未登录用例应返回 401，实际 403 → 断言失败 | 不改时顺序正确 |

### 5.4 记录模板（必须四列，缺列即未做）

| 变异编号 | 文件:行 | 变异内容 | 期望怎么红（哪条断言） | 对照组 rc | 变异后 rc | 撤销后 rc | 结论 |
|---|---|---|---|---|---|---|---|
| M-01 | `src/auth.py:41` | `>` 改 `>=` | `test_zero_age_rejected` 应失败 | 0 | 1 | 0 | 真抓 |
| M-02 | `src/api.py:88` | 删 `raise` | `test_bad_token_raises` 应失败 | 0 | 1 | 0 | 真抓 |
| M-03 | `src/db.py:12` | 改表名 | 全部用例报错 | 0 | 2 | 0 | **假红**：rc=2 是崩了不是抓到，改用例重做 |

**判读规则**：
- 对照组 rc≠0 → 环境问题，先修环境，本轮变异作废。
- 变异后 rc=2 → 崩了，不是抓到，⛔ 不算变异成功。
- 变异后 rc=1 但红的断言与变异点无关 → 判据抓错了对象，需补针对性断言。
- 撤销后 rc≠0 → 撤销不干净，⛔ 不许继续（后续结果不可信）。

## 七、反例

**反例 1：只跑红的半边**
> 「M-01 把 `>` 改成 `>=`，测试红了，证明变异被抓到。」

错在哪：没对照组就无法排除「本来就红」。也可能红的是别的用例。判据上：记录里对照组列为空 → 视为未做变异。

**反例 2：拿 rc=2 当「抓到了」**
> 变异后脚本 Traceback 退出码 2，记录写「变异成功，测试报错」。

错在哪：rc=2 是脚本自己崩了，属「判据不可用」；真抓到必须是 rc=1（业务判据红）。`00_工程规范.md` §三 明确 rc∈{2,3} 是没结论。

**反例 3：用正常数据测异常分支**
> 反例用例传了一个合法用户但密码对，断言「不报错」。

错在哪：走的是正常分支，兜底逻辑零覆盖，全绿但毫无意义（依据：`00_工程规范.md` §八 第 1 条）。

**反例 4：变异后改判据让它变绿**
> 变异后发现测试红了，于是把断言从 `== 401` 放宽成 `!= 200`。

错在哪：这是**拆闸**不是修 bug。变异的意义就是逼出判据的漏洞，此处应补强断言，⛔ 不许放宽。若确需放宽，必须留审计行（时间/原因/责任人/如何再收紧）。

**反例 5：一次变异改三处**
> 同一次变异同时改了校验、返回值、日志。

错在哪：红了也说不清是哪处抓到的，等于没测。一次一处，逐条记。

**反例 6：反向变异只测「该红的红了」，不测「不该红的没红」**
> 没有对照组，也没有「合法输入仍通过」的断言。

错在哪：单向判据允许交付方靠「一律报错」糊弄过去（依据：`00_工程规范.md` §五 双向要求）。

## 八、与上下游的衔接

**允许进入 S4 的条件（全满足）**
1. 三面用例齐，测试命令 rc=0，且用例数与覆盖自证对得上。
2. 反向变异每组都有「对照组 rc=0 / 变异后 rc=1 / 撤销后 rc=0」三值。
3. 无「假红未重做」的残留行。
4. 静态门 rc=0。
5. 闸三 rc=0。

**必须退回的情况**
- 对照组起不来（环境坏、依赖缺失）→ 停在 S3 修环境，⛔ 不许带病做变异。
- 变异抓不到（改坏了测试还绿）→ 判据无效，回 S2 补验收点、回 S3 补断言；⛔ 不许把「抓不到」记成「通过」。
- 发现验收点本身写错（不可能满足）→ 退回 S2 改计划，必要时退回 S1 改冲突归属。
