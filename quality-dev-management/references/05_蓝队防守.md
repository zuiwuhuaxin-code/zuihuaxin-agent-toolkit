# S5 蓝队防守

> 位置：红队报告之后，独立审查之前。
> 本阶段唯一不可替代的价值：**把红队发现的点状缺口，补成事前能防、事中能断、事后能追的连续链路**。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 三段齐全 | 事前 / 事中 / 事后各有机制条目，⛔ 缺一段不算完成 |
| 机制可定位 | 每条机制挂 `file:line` 或配置项路径 |
| 缺口有归属 | 每条 `E-xx` 至少被一段覆盖，未覆盖的必须写理由 |
| 闸门分层合规 | 四层闸门职责与可关性符合`00_工程规范.md` §七，⛔ 不另造模型 |
| 无 silent-off | 每道闸写清「能否关 / 关了会怎样 / 关闸是否告警」 |
| 可验证 | 每条机制配一条验证方式（用例 rc / 日志字段 / 命令） |

闸：`acceptance_gate.py` 检查防御报告含「事前」「事中」「事后」三节，且每节至少 3 条机制行。rc=0 才进 S6。

## 二、输入

1. S4 红队报告（五列表 + 轮次表）——这是本阶段的缺口清单来源。
2. 加固后的代码（S4 已修的 `F-xx`）。
3. 部署形态与运行环境（决定哪些机制真能落地）。

**前置检查**：红队报告里每条 `block` 是否真修了？没修就先回 S4。⛔ 不许拿「设计中的加固」当已落地。

## 三、三段各自要写什么

### 3.1 事前防御（Prevention）——让缺口根本不出现

写什么：**在代码进入主干之前**就拦住的机制。

| 机制类型 | 具体写法 | 判据 |
|---|---|---|
| 输入契约收紧 | 参数白名单、类型注解 + 运行时校验、拒绝而非纠正 | 有校验函数 `file:line` + 反例用例 |
| 默认安全 | 默认拒绝（deny by default）、默认关调试、默认最小权限 | 配置项与默认值 |
| 凭证治理 | 环境变量 / 密钥管理，⛔ 仓库零明文；`.env.example` 只放占位 | `grep` 明文凭证命中数 = 0 |
| 依赖治理 | lock 文件、固定版本、官方源 | lock 文件存在 + 校验和 |
| 最小暴露 | 只开必要端口/路由，内部接口不注册到公网路由 | 路由表 + 部署清单 |
| 静态门 | lint / type check / 密钥扫描挂在提交前 | 命令 rc=0 |

对应闸门层：**第 1 道 `pre_commit`**（本地可关，快速反馈）+ **第 3 道 `ci_required`**（服务端必过）。

### 3.2 事中阻断（Detection & Blocking）——出事时当场拦住

写什么：**运行时**发现异常并阻断/降级的机制。

| 机制类型 | 具体写法 | 判据 |
|---|---|---|
| 鉴权与归属校验 | 每个入口一句 `assert_can(user, resource)`，集中实现 | 覆盖入口数 / 总入口数 |
| 限流与配额 | 按主体（用户/IP/租户）计数，超限拒绝 | 阈值配置 + 超限用例 rc |
| 输入运行时校验 | 反序列化前后都校验，拒绝未知字段 | 用例断言 4xx |
| 失败关闭（fail-closed） | 依赖不可用时**拒绝**而非放行 | 桩掉依赖 → 断言拒绝 |
| 异常不外泄 | 对外统一错误码，堆栈只进内部日志 | 响应体无 `Traceback` / 无路径 |
| 告警 | 关键拒绝事件立刻告警（不是只写日志） | 告警通道 + 触发条件 |
| 降级档位 | 中低置信只 warn 不 block，且 warn 留痕可升级 | 审计行五要素齐 |

对应闸门层：**第 2 道 `pre_receive`**（服务端推送归口，⛔ 不可关）+ **第 4 道 `artifact_scan`**（制品/运行时，最后一道防线）。

⚠ `00_工程规范.md` §七的两条真实边界（⛔ 不许假装不存在）：
1. `--no-verify` 能跳过 pre-commit ⇒ 第 1 道只是「提前拦」，不是唯一防线；pre-push 对共享分支要**重跑**检查。
2. GitHub 托管版不支持自定义 pre-receive ⇒ 等价手段是分支保护 + required checks，且必须**取消勾选 `Include administrators`** 才真拦得住管理员。

### 3.3 事后追溯（Forensics & Recovery）——出完事能查清、能恢复

写什么：**事后**能回答「谁、什么时候、做了什么、影响了什么」的机制。

| 机制类型 | 具体写法 | 判据 |
|---|---|---|
| 审计日志 | 结构化（JSONL），字段：时间/主体/动作/对象/结果/请求 id | 字段齐 + 一条真实样本 |
| 不可篡改 | 追加写、只增不删、异地/只读副本 | 写模式 + 存储位置 |
| 敏感脱敏 | 日志字段白名单，凭证/证件/手机号不落盘 | 白名单 `file:line` + grep 无明文 |
| 可回放 | 关键操作可从日志重建（输入参数留存，敏感项脱敏） | 抽一条日志能复现 |
| 应急响应 | 事件分级 + 处置步骤 + 谁通知谁 | 一页 runbook |
| 恢复与轮换 | 凭证泄露的轮换清单、数据回滚点 | 轮换清单 + 回滚命令 |

**判据底线**：事后段不能只有「我们会记日志」。必须有「日志在哪、谁能读、读出来能干什么」。

## 四、操作步骤

**E1 建三段 × 三问矩阵**
对每条 `E-xx` 填：防什么（E 编号）/ 用什么机制（`file:line`）/ 怎么证（rc、用例、日志字段）。

**E2 补缺口**
矩阵里出现「无机制」的格子 → 要么补机制，要么在该段写「不覆盖 + 理由 + 由哪段兜底」。⛔ 不许留空格。

**E3 定闸门档位**
按`00_工程规范.md` §七：高置信 → block；中低置信 → warn（留痕 + 责任人 + 可升级）。⛔ 无 silent-off。

**E4 写「关闸后果」**
每道闸写：谁能关、关了会怎样、关闸是否告警、告警发到哪。这一列是给审查方查「有没有静默关闭」用的。

**E5 自证**
跑一遍验证：`grep` 明文凭证 = 0；桩掉依赖断言拒绝；日志样本字段齐；每条机制的命令 rc 记录。

**E6 收口出报告**

|---|---|---|---|---|---|

### 5.2 闸门分层表（照抄`00_工程规范.md` §七，⛔ 不造新模型）

| 层 | 名称 | 能否本地关 | 本项目的落点 | 关闸后果 / 告警 |
|---|---|---|---|---|
| 第 1 道 | `pre_commit` | ✅ 可关 | `.githooks/pre-commit` 跑 lint + 密钥扫描 | 关了仅少一层快速反馈；告警：无（可关层） |
| 第 2 道 | `pre_receive` | ⛔ 不可关 | 分支保护 + required checks | 无法关闭；管理员绕过需取消勾选 |
| 第 3 道 | `ci_required` | ⛔ 不可关 | CI 必过任务 | 关闭即视为违规，须审计行 |
| 第 4 道 | `artifact_scan` | ⛔ 不可关 | 制品扫描 | 关闭即视为违规，须审计行 |

⚠ **不许宣称「服务端已把守」**：服务端三层的激活状态以**远端实际配置**为准，客户端只能提供配置与自证。未实测配置前，写「配置已提交，激活状态未核实」。

## 六、反例

**反例 1：只有事中一段**
> 「已加鉴权、已加限流、已加日志。」报告三段合一，没有明确的事前与事后。

错在哪：事前缺失 = 缺口靠运行时兜（成本最高、必漏）；事后缺失 = 出了事查不清，等于没有可追溯性。三段是链路，不是三选一。

**反例 2：把 try/except 当防御**
> 事中机制写「所有入口加了 try/except，异常被捕获」。

错在哪：捕获不等于阻断，也不等于记录。没写日志字段 = 事后查不到；吞掉异常 = 静默失败（`00_工程规范.md` §八 第 9 条 明令禁止静默回落）。防御机制要能回答「拦住了什么、记下了什么」。

**反例 3：fail-open 冒充 fail-closed**
> 「依赖不可用时跳过校验，保证服务可用。」

错在哪：这就是把闸拆了。安全场景必须 fail-closed：依赖挂了就拒绝。若要可用性优先，必须显式写「这是可用性取舍，风险已接受，责任人 X」，不能包装成防御。

**反例 4：自称服务端已把守**
> 「已配置分支保护，服务端不可绕过。」

错在哪：未实测远端配置就宣称生效，违反`00_工程规范.md` §七「不凭客户端代码宣称服务端已生效」。正确写法：配置已提交 + 激活状态未核实 + 谁去核实。

**反例 5：日志记了敏感数据**
> 审计日志记完整请求体，含手机号与 token。

错在哪：事后追溯机制自己变成泄露源。日志必须字段白名单 + 脱敏。

**反例 6：另造一套闸门模型**
> 自创「三级防护：基础/增强/兜底」，与四层闸门对不上。

错在哪：两套模型必然漂移，S6 审查方无法对照。⛔ 一律沿用`00_工程规范.md` §七的四层命名与可关性。

## 七、与上下游的衔接

**允许进入 S6 的条件（全满足）**
1. 三段齐全，每段 ≥3 条机制，全部挂 `file:line` 或配置项。
2. 每条 `E-xx` 有覆盖段，或明确写「不覆盖 + 理由 + 兜底段」。
3. 四层闸门表齐全，每层有「能否关 / 关闸后果」。
4. 无 silent-off 表述。
5. 至少一条 fail-closed 自证、一条日志样本、一条 `grep` 明文凭证 = 0 的记录。
6. 闸 rc=0。

**必须退回的情况**
- 发现某条 `E` 在 S4 根本没修 → 退回 S4，⛔ 不许在 S5 用「设计中的机制」补。
- 某段机制全都落不了地（无部署条件）→ 退回 S2 加任务，或降级为 `warn` 并写明。
- 需要改 PRD 的安全策略（例：PRD 要求明文导出）→ 退回 S1 冲突清单。
