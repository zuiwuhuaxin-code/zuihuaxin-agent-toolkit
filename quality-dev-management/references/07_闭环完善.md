# S7 闭环完善

> 位置：独立审查报告之后，源码汇总之前。
> 本阶段唯一不可替代的价值：**以审查报告为唯一整改依据，改到验收闸门 rc=0**。⛔ 不许自己另立标准，也不许顺手重构。

## 一、目标与判据

| 目标 | 判据（可观察） |
|---|---|
| 整改有据 | 每条整改都能追到审查报告的 `报告行号`，无「无来源改动」 |
| 整改全覆盖 | 对照表无「未整改」行；Blocker 100% 关闭 |
| 改动范围受控 | 只改报告点到的位置（+ 必要的最小连带），`git diff --stat` 可核对 |
| 回归不破 | 全量自测 rc=0，原有绿灯用例仍绿 |
| 变异仍有效 | 反向变异重跑，仍有「对照组绿 / 变异红 / 撤销绿」三值 |
| 验收达标 | `python scripts/acceptance_gate.py <清单>` → rc=0 |

出关判据：闸 rc=0 **且** 对照表无未整改行 **且** `git status` 干净（改动都已提交或明确列在交付说明）。

## 二、输入

1. 独立审查报告（**唯一整改依据**）。⛔ 不许拿自测记录、红队报告、自己的想法当追加依据。
2. S7 之前的代码版本（作为 diff 基线，记 commit 或文件哈希）。
3. 验收清单 JSON（S2 的验收点汇总，转成 `acceptance_gate.py` 可消费格式）。

**前置检查**：给当前代码打一个基线标记（commit 或 `sha256` 清单），否则改完无法证明「只改了该改的」。这也是「续跑先比指纹」的前提（依据：`00_工程规范.md` §九 第 4 条）。

## 三、操作步骤

**G1 条目化**
把审查报告每条（B-xx / S-xx / N-xx）转成整改任务，编号 `R-xx`，保留指向：`报告行号 → R 编号`。

**G2 定范围**
每条写「改哪个文件哪段」。判据：改动若超出报告描述的范围，必须单列理由（例：修 B-01 需要连带改调用方签名）。

**G3 逐条整改**
按优先级（Blocker → Suggestion → Nit，Nit 可批量但须列明）逐条改。⛔ 不顺手重构、不顺手格式化整文件（会把 diff 淹掉，审查方无法复核）。

**G4 每条配证**
每条整改必须配一条「怎么证改对了」：新增/修改的用例、或一条可跑命令 + 期望 rc。⛔ 「改完了」不是证据。

**G5 全量回归**
跑全量测试 rc=0；跑静态门 rc=0；跑 `acceptance_gate.py` 看 rc。

**G6 重跑反向变异**
对**新增/修改的判据**做变异（老判据不必重跑全部，但正例链路要抽验）。仍要求三值：对照组 rc=0 / 变异后 rc=1 / 撤销后 rc=0。

**G7 出对照表 + 交付说明**
对照表逐条闭环；交付说明写清单、rc 记录、未整改项（若有，须写明理由与承接人）。

**G8 收工**
`acceptance_gate.py` rc=0 → 进 S8。rc=1 → 回 G3。rc=3 → 先修清单/环境（判据不可用 ≠ 通过）。

## 四、输出模板

### 4.1 整改对照表（本阶段核心产出）

| R 编号 | 报告行号 | 级别 | 问题摘要 | 改法 | 改后 file:line | 验证方式 | 状态 |
|---|---|---|---|---|---|---|---|
| R-01 | `06_独立审查报告.md:88` | 🔴 | 导出缺归属校验 | 查询加 `owner_id` 条件 | `src/export.py:61-66` | `tests/test_export.py::test_other_user_403` rc=0 | 已闭环 |
| R-02 | `06_独立审查报告.md:104` | 🟡 | 上传未拒双扩展名 | 白名单 + 后缀二次判定 | `src/upload.py:34-40` | `test_double_ext_rejected` rc=0 | 已闭环 |

**状态列只允许三种值**：`已闭环` / `不整改（理由 + 承接人）` / `阻塞（原因 + 需要谁）`。⛔ 不许留空、不许写「部分完成」。

## 五、反例

**反例 1：顺手重构**
> 修一条 Blocker，顺手把整个模块的函数拆了、命名改了。

错在哪：审查报告的 `file:line` 全部失效，S6 无法复核整改是否到位；且新引入的代码没有任何审查覆盖。依据 `00_工程规范.md` §九「只重做有问题的部分」。

**反例 2：自己在报告外加需求**
> 「审查没提，但我觉得这里也该加个缓存，一起改了。」

错在哪：整改依据必须唯一。加了报告外的改动，等于把未审代码塞进终版。要做就单列「建议新增项」，交给下一轮审查。

**反例 3：整篇重写**
> 报告 5 条，代码整个文件重写了一遍。

错在哪：无法证明「只改了该改的」，回归风险不可控，diff 也不可读。极端情况才允许重写，且必须单列理由并重新走 S6。

**反例 4：把「改不了」写成「已评估，影响可接受」**
> R-03 状态写「已评估风险可接受」。

错在哪：这是审查方（或用户）的裁决权，不是施工方的。正确写法：`不整改（理由：需要改表结构，超本期范围）+ 承接人：<谁>+ 已上报待裁`。

**反例 5：把闸 rc=3 当通过**
> `acceptance_gate.py` 报 rc=3（清单里某个路径不存在），交付说明写「闸已跑」。

错在哪：rc=3 是判据不可用 = 没结论，既不是通过也不是检出（`00_工程规范.md` §三）。必须先修清单或环境再跑。

**反例 6：改完不重跑变异**
> 「只改了几行，之前变异都过了。」

错在哪：整改常常正是修改判据本身，判据一改，之前的变异结论全部失效。新判据必须重新变异验证。

## 六、与上下游的衔接

**允许进入 S8 的条件（全满足）**
1. 对照表覆盖审查报告全部条目，状态列无空值。
2. 所有 Blocker 已闭环；未闭环的 Suggestion/Nit 有理由与承接人。
3. 全量测试 rc=0、静态门 rc=0。
4. `acceptance_gate.py` rc=0。
5. 新增/修改的判据做过变异，有对照组三值。
6. `git diff --stat` 与报告范围对得上，超范围改动有理由。

**必须退回的情况**
- 某条 Blocker 改不动（需改 PRD / 需改架构）→ 退回 S1 冲突清单，或退回 S2 加任务，⛔ 不许在终版留 Blocker。
- 整改引发大面积回归 → 用回滚点退回该任务基线，重新按 S2 走（⛔ 不许在原位上反复打补丁）。
- 审查报告本身不合格（条目无 `file:line`）→ 退回 S6 重审，⛔ 不许照着模糊条目猜着改。

## 七、自检清单

- [ ] 对照表行数 = 审查报告条目数（不多不少）
- [ ] 每条有 `报告行号`、`改后 file:line`、`验证方式`
- [ ] 状态列只有三种合法值，无空值
- [ ] Blocker 全部「已闭环」
- [ ] `git diff` 只覆盖报告范围（或超范围有理由）
- [ ] 全量测试 rc=0，原有绿灯用例未被删改绕过
- [ ] 新判据做过变异，三值齐（0/1/0）
- [ ] `acceptance_gate.py` rc=0（不是 1，也不是 3）
- [ ] 交付说明写了基线 commit 与指纹
